## 调度与恢复

运行正式 `packages/platform/test/node/scheduler.integration.test.ts`，2026-10-14 **11:57:28.006 UTC → 11:57:54.108 UTC**，9 项通过、1 项长时钟用例未运行。该长时钟要求由下文正式生产 web 的独立 601 秒场景覆盖。脱敏测试结果见 [结果](b-6.1-scheduler-results.json)，持久 metadata 见 [ledger / callback / effect / native 状态](b-6.1-scheduler-ledger.json)。

- Asia/Singapore `0 2 * * *` 持久计划为 `2030-01-01T18:00:00Z`，即当地次日 02:00。handler 收到原计划 Date，ledger 保持一致。这里是正式 cron-parser 和 scheduler 的指定时间映射验证，未等待每日 02:00。
- 秒级 cron 的双 jobs 互斥：计划 `11:57:31 UTC`，实际 callback `11:57:32.193954 → 11:57:35.398804 UTC`，持续 3.204850 秒；跨后续 slot 的再次竞争仍只有一个 ledger、一个 callback、一个业务效果。此秒级长任务只验证跨 slot，未称为 1–2 小时采集流水线。
- 真实停机 3.3 秒错过多个秒级 slot，双实例重启后 `once` 仅执行最近 `11:57:40 UTC`，唯一效果；`skip` 没有停机补跑，下一正常计划 `11:57:41 UTC` 执行。
- 已开始的 skip 任务 SIGKILL 恢复：原 ledger `01a13a46-826e-7547-81b7-116fccd36fb3`，两个 callback 记录保持同 workflow `schedule-run:01a13a46-826e-7547-81b7-116fccd36fb3` 与原 `11:57:42 UTC` 计划，恢复后仅一个幂等效果。SIGTERM 未完成运行同样恢复原身份。
- 额外复用正式回归覆盖 claim 后发布前退出、成功 checkpoint 后完成 ledger 写入失败、owner 连接失权但旧进程存活时禁止接管及迟到完成。

该正式 suite 的多数双实例/恢复场景使用手动 tick，停机/跨 slot 等待经过真实 wallclock，但不将手动未来 tick 称为自主准时触发。上述指定时间 tick 与快速 suite 的模拟陈旧心跳均局限于 `b_accept_scheduler`，不作为正式 web 的真实时钟证据。生产健康使用独立的 `b_accept_health`；未写入、修改或删除其 heartbeat 来推动验收。

追加自主双实例场景在独立 `b_accept_autonomous` 库运行，[脚本](b-6.1-autonomous-run.mjs) 复用正式 scheduler worker / adapter，配置 `*/2 * * * * *`、Asia/Singapore，两个 jobs 均调用 `scheduler.start()`；没有 tick、prepareAt 或时间注入。[原始快照](b-6.1-autonomous.json) 显示计划 `12:08:48.000 UTC`，ledger 实际开始 `12:08:48.358 UTC`，callback 开始 `12:08:48.468 UTC`（偏差 468ms），完成 `12:08:51.989 UTC`（callback 持续 3521ms）。在 `12:08:51.012 UTC` 已跨下一 slot，仍只有一个运行与 callback，最终一条业务效果。这验证自主时区 cron 触发与跨 slot 互斥，02:00 的 UTC 映射仍由前述独立指定时间场景证明。

自主场景的初轮观察脚本把 Date 对象传给 `Date.parse`，字符串转换丢失毫秒，误报 3000ms 并使断言失败；[初轮原始 metadata](b-6.1-autonomous-preliminary.json) 保留。改用 `new Date(value).getTime()`，保持原断言，在上述独立库重新完整运行通过，未弱化断言或改动生产代码。
