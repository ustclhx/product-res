# B 6.3 本地 Docker 长流水线验收

本轮使用正式 Node adapter 与既有 `packages/platform/test/node/workflow.integration.test.ts`
场景，PG 为本 worktree 独占 Docker 容器；Node worker 在宿主机运行。
原型、旧报告、fake timer 与数据库时间回填不参与本轮通过判定。

固定源码：`70496c6496ca7f2b89ea75a49f1a6629836fe628`；DBOS SDK `5.2.11`；
Node `23.11.0`。应用测试版本 `workflow-integration-v1`，handler/步骤顺序在重启期间不变。
PG 精确版本及镜像身份、实际 UTC 起止和结果见同目录 JSON 证据。

复现使用独占 PG17，migrator 应用已有业务迁移，再由 suite 调用公共 DBOS migrate。
app 只有 DML；readonly 只读受限 metadata。连接值仅加载受限、被忽略的环境文件，
配置 `MIGRATION_DATABASE_URL`、`TEST_JOB_DATABASE_URL`、`TEST_JOB_MIGRATOR_URL`、
`TEST_JOB_READONLY_DATABASE_URL`，不要输出这些变量。

```sh
pnpm --filter @product-res/db db:migrate
TEST_WORKFLOW_LONG=1 pnpm --filter @product-res/platform exec vitest run \
  --config vitest.workflow.config.ts -t 'real 61-minute'
```

快验使用另一个逻辑数据库，避免不同 handler 注册集互相领取：

```sh
pnpm --filter @product-res/platform exec vitest run --config vitest.workflow.config.ts
```

长跑形状：列表 → 五次真实 Drizzle 事务额度副作用与每批两条详情 →
持久节奏 sleep → 长 sleep → 早到事件 → 归并 → 汇总。无外部采集 API。
额度/详情为模拟业务表中的幂等写入；队列的正式 2 并发/10 秒 3 次限额由 B 6.2
另行验证，不把本流水线顺序详情的 100ms 节奏说成生产 API 配额策略。

故障注入在第一段 sleep、带原 deadline 的 wait、完成列表/额度/详情后的长 sleep：
SIGKILL 原 worker，确认其退出后，以相同 executor、handler、业务 ID 与版本重启。
原 deadline、七个 sleep 原唤醒时刻和已成功 callback 计数由测试前后直接比对。
早到事件在首次创建后发送，真实保留超过 3600 秒再消费。

快验独立覆盖副作用提交后/native checkpoint 前强制退出：callback 可重做两次，
业务幂等结果一次；事件已原子消费/native checkpoint 前退出后，JSON null 结果仍
可恢复而不再次消费；不可重试 Provider 失败仅执行一次提交和一次释放预扣。
这证明模拟副作用及结算幂等，不宣称任意外部副作用 exactly-once 或跨代码版本热重放。

资源采样见 `b-6.3-resources.jsonl` 与汇总 JSON：每约一分钟记录 Docker PG CPU/working set、
数据库连接与关系 footprint、cluster WAL LSN、宿主 Node worker RSS/CPU。PG 限制 2 CPU/1GiB，
宿主 Node 没有 cgroup 限额；短时快验在同 PG 的另一逻辑库运行，PG CPU/WAL 是合计值。
这里只报告本地观察，不代表 web/Valkey/代理/双 jobs 整机 2 核 4GiB 验收。
服务器与整机资源门槛仍为未完成的 6.4。

## 本轮通过结果

[最终 metadata 与独立复核](b-6.3-workflow-final.json) 与
[重启后长 sleep 基线](b-6.3-workflow-baseline.json) 来自同一数据库、同一 native/业务身份。
原生运行 **2026-10-14 11:55:48.631 UTC → 12:56:56.032 UTC**，持续
**3667.401 秒（61.123 分钟）**，SUCCESS，recovery_attempts=4（首次加三次同版本重启）。
Vitest 长跑一项通过，完整命令耗时 3668.89 秒；快验另库十项通过、耗时 115.87 秒。

早到事件 **11:55:48.644102 UTC** 写入，**12:56:56.009578 UTC** 消费，保留
**3667.365476 秒**。列表、五次额度、十条详情、归并和汇总共 18 个 callback 各一次；
15 条额度/详情幂等结果完整。七个原 sleep 唤醒值与基线逐项相同，
原 resume deadline **11:56:52.673720 UTC** 未变化，两个事件均消费一次。
测试同时断言输出 total=10、API timestamp 为 Date 且等于原发送时间；报告不读取业务 payload。

[快验故障/结算证据](b-6.3-workflow-fast.json) 中，副作用窗口 callback 两次、幂等效果一条；
不可重试 submit 与 settlement 各一次、release-hold 一条。原子事件结果恢复和晚到 deadline
拒绝、FIFO、停止接收、最短保留期权限等既有正式用例均通过。

资源原始采样中的关系聚合对表及索引重复计数，发布时明确命名为
`journalRelationFootprintSumBytes`，只用于趋势；最终 `journalTableBytes` 用
`relkind IN ('r','m')` 过滤后汇总 `pg_total_relation_size`，索引只计一次。
WAL 为整个 PG 集群，包含另库快验；宿主 CPU 是 ps 生存期平均值。
[资源汇总](b-6.3-resource-summary.json) 记录准确统计方法、镜像 digest、峰值与 OOM 计数，
不将这些观察解释成服务器/整机预算签收。
