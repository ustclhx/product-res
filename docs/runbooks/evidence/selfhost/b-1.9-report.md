# B 1.9：2 vCPU/4GiB 资源预算与选型复核

本轮只执行 `add-selfhost-job-engine` **1.9**。正式镜像来源为
`081305013b022f457c561eecf5828b1959e13908` 的 GHCR digest，重用 D 已核验的
[八镜像集合](d-bundle2-2026-10-14/image-set.json)。没有重建业务镜像、请求外部业务 API、
写共享 staging 或改生产 Compose/schema/依赖。新加坡服务器 6.4 保留未完成。

## 测量边界与复现

独占 **Colima `b-budget`，Linux/arm64，2 vCPU/4GiB、30GiB 磁盘**，
不改变全局 Docker context。所有容器、网络与卷使用 `b-budget` 前缀。
正式 web、PG、Valkey、Caddy、双 jobs 共用该 VM；迁移先于 apps。镜像匿名拉取，
digest、Node/DBOS、PG 与 VM 可见内存见 [runtime](b-1.9-runtime.json)。
VM 配置4GiB与Linux MemTotal并不相同；判定余量使用真实 MemAvailable，不只累加容器RSS。

资源原始数据：[每阶段及分钟采样](b-1.9-resources.jsonl)。记录 Docker 单核口径CPU、
working set、逐容器 `/proc` RSS 合计、cgroup current/peak/events/cpu.stat，
VM meminfo/stat/pressure、集群连接/WAL LSN、数据库大小和 journal 表及索引 footprint。
RSS含PG共享页，不能相加当真实整机内存；Docker working set不等于RSS，memory.peak含page cache。
`relkind IN ('r','m')` 后才合计 `pg_total_relation_size`，避免索引重复计数。
WAL属于整个PG集群，含业务、探针、升级及清理，不按单引擎归因。

模拟队列/长任务使用正式 migrate 镜像中的 `/src` Node adapter，在同PG的独立
`b_budget_probe` 库运行，不把探针注册集混入正式 jobs。两个额外worker注册同版本完整handler，
稳定互异hostname/executor、共享owner卷；额外pool/RSS也计入VM实测。
正式双jobs保持生产10条/5秒批次；压力探针采用2条/250ms聚合、并发2、3条/10秒、
首批90条、完整profile后追加90条真实caller Drizzle事务入队与100ms模拟callback。该较紧聚合窗用于资源观察，
不替代 [B6.2](b-6.2-queues.md) 的完整重试/DLQ/10条5秒行为验收。

长任务在成功step后持久sleep **3661秒**，早到事件在创建时发送；中途停止/重启后继续。
真实钟用于长时长、早事件与恢复判定；模拟清理时钟只验证保留边界，二者分开记录。
公开TLS请求额外执行160次、并发最多4，页面与health全部200：
[HTTP负载](b-1.9-http-load.json)。自然五分钟slot后公开HTTPS health200，版本为完整SHA；
没有回填 `jobs.lastCronAt`。

在清理后的机器从仓库根运行：

```sh
python3 docs/runbooks/evidence/selfhost/b-1.9-run.py
```

[复测入口](b-1.9-run.py) 复用既有release verifier/secret/证书生成，拉取固定digest，
创建独占VM与空卷，执行基础双jobs及90条积压、idle、61分钟事件/重启观察，finally清理。
可选接线开启后再追加90条消息，最终要求合计180个副作用各一次。
拒绝复用已有同名VM，输出在 `test-results/b-budget-replay-<时间>/`，不覆盖本轮证据。
[探针](b-1.9-probe.mjs) 与 [采样器](b-1.9-sampler.py) 可分别复用。
本轮按这些组件的分阶段命令执行；复测入口未另重复等待一次完整61分钟。
可选服务与升级复核的具体步骤和本轮结果另见下文，基础复测入口不代验它们。

## A/D 全服务预算

| 服务 | 已发布基础 cap CPU/MiB | 本地基础预算变体 CPU/MiB |
| --- | --- | --- |
| PG | 0.5 / 1024 | 0.5 / 1024 |
| Valkey | 0.2 / 384 | 0.1 / 256 |
| web | 0.5 / 1024 | 0.4 / 768 |
| jobs ×2 | 0.3 / 768，各实例 | 0.3 / 512，各实例 |
| Caddy | 0.2 / 128 | 0.1 / 128 |
| 常驻合计 | **2.0 / 4096** | **1.7 / 3200** |
| migrate，一次性 | 0.3 / 512 | 在启动apps前运行 |

基础发布配置原为一个jobs，常驻3328MiB/1.7核；直接增加同配额第二jobs后没有宿主内存预留。
这是配额算术，不意味着测试一定OOM；不能以本轮低使用量宣布默认cap总预算有余量。
本地变体只改任务运行的cap，生产配置保持原样；配置4GiB口径留896MiB，实际宿主余量取VM数据。

旧 [spike预算](../../../../openspec/changes/add-selfhost-job-engine/spike/resource-budget.md)
是未签收建议，native pool5/连接41已过时。当前默认连接预算为
**web10 + 双jobs×(业务10 + native4) = 38**；ownership借自native4，不另增加连接。
健康检查借现有池，migrator在apps前执行；本轮两个额外探针另加最多28连接，
升级/维护短进程另计。PG连接上限与观测峰值见汇总，不把池的max当持续使用值。

可选profile必须另预算：发布storage会降web/jobs至768/512MiB、加512MiB/0.3核storage，
单jobs常驻3328MiB/2核；第二jobs再加512MiB/0.3核。backup默认384MiB/0.2核。
因此发布storage+双jobs+backup配额为**4224MiB/2.5核**，不能直接宣称整机2C/4G留余量。
A/C/D旧轮测量分开引用，不能把不同机器的峰值相加当本轮整机峰值：
[C profile](../../selfhost-c-profile.md)、[D备份](../../selfhost-backup.md)、
[A基础Compose](../../selfhost-a7.md)、[A完整双jobs验收](../../selfhost-a-final.md)。

## 可选服务合并复测

[完整profile配置与归档](b-1.9-all-profiles.json) 使用同一正式object-storage/backup镜像。
在原PG卷上启用archive_mode=on、60秒archive_timeout；停止应用再重建PG，随后恢复所有jobs。
应用storage bucket为任务专用 `b-budget-files`；备份使用独立应用身份/`b-budget-backup` bucket、
独立SeaweedFS实例及私有TLS gateway，没有向web/jobs分配backup凭据或PG socket。
该S3替身/gateway额外512+128MiB/0.4核也在同VM采样，但不计作使用外部S3时的生产常驻cap。
其application权限是专用bucket Read/Write/List/Tagging，并非严格prefix ACL或仅Write。

| 完整本地变体 | PG | Valkey | web | jobs×2 | Caddy | storage | backup | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| cap MiB | 1024 | 192 | 640 | 384，各实例 | 128 | 512 | 256 | **3520** |
| cap CPU | 0.5 | 0.1 | 0.3 | 0.2，各实例 | 0.1 | 0.3 | 0.2 | **1.9** |

这是本轮小负载预算变体，配置4GiB口径给宿主576MiB；真实余量由VM MemAvailable复核。
backup默认384MiB未直接套用；256MiB在本轮小库base/dump/归档校验下复测。
不能从该小库推出大数据库备份、业务峰值、所有扩展同时启用都已满足此cap。

[备份结果](b-1.9-backup.json) 包含首次失败与重试：本地gateway临时Caddyfile的内联block
格式错误造成首次base未通过；仅修正fixture格式后，正式cycle exit0，base/dump/verification/
archive/retention状态成功、health为true。schedule首次失败记录仍保留；17:23的自动重试随后成功，末态healthy为true，
不伪造从未失败。
未执行PITR/异地复制/异机恢复；这些不是1.9资源预算可以代签的部署验收。

[storage负载](b-1.9-storage-load.json)：4路并发，3轮，每对象16MiB，共12对象/192MiB，
通过真实TLS/S3签名PutObject及HeadObject长度核对；同时所有正式服务和探针都在VM运行。
大文件只保存在本次命名卷，结束清理，不请求外部对象存储或AI。

完整基础复测运行中取得 `runtime.ready` 的路径，在第二终端执行：

## Schema、迁移与权限

自有 `job_engine` 为9表：queue/batch/message/start/dead_letter、workflow_event/workflow_wait、
schedule/schedule_run；native `dbos` 由固定SDK拥有。业务SQL与公共DBOS migrator按序初始化空卷，
重复正式migrator exit0；运行中的app/jobs未授予DDL，也未启用自动迁移。
app CREATE/ALTER、readonly message.body/event.payload读取和写入均实际被拒绝，
readonly metadata成功；随后用真实app/readonly账号经verify-full TCP复核，
拒绝项SQLSTATE均为42501，逐条SQL与结果已保存。具体checks、schema清单见 [runtime](b-1.9-runtime.json)。

升级复现入口 [b-1.9-upgrade.py](b-1.9-upgrade.py) 使用同一 `--runtime <路径>`；
仅创建独立逻辑库/临时旧SDK，不重启PG。另在同PG的 `b_budget_upgrade` 隔离库，用精确 **5.1.10 CLI schema** 初始化与重跑。
5.2.11 app probe返回 `JOB_ENGINE_DATABASE_NOT_READY`；公共migrate升级两次后app probe started：
[本轮升级证据](b-1.9-upgrade.json)。旧SDK仅安装在一次性migrate容器临时目录，
根manifest/lockfile与正式镜像没有变化。不能据此推导任意未来SDK兼容或跨代码版本热重放。

保留期沿用 [Node引擎runbook](../../node-job-engine.md)：消息/batch/owned journal7天、DLQ30天，
start至少max(60分钟、配置、滑动速率窗)；event/wait7天、最短60分钟。
active和未知native终态/更新时间不删；只用public deleteWorkflow删owned queue-batch。
[本轮模拟超期清理](b-1.9-active-retention.json) 中30条已终态消息和15个owned journal删除，
60条active消息、1个active batch、长workflow与未消费早事件完整保留；小于60分钟的配置被拒绝。
模拟清理发生在积压中，footprint/WAL趋势包括这次维护，物理大小不因删行立即缩小。
