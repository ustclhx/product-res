# 06 · AI：文本、图片、视频

## 1. 总体设计

| 类型 | 执行方式 | 可选计费方式（按模型配置，见 §2） | 状态存储 |
|---|---|---|---|
| 文本 | 请求内流式（`streamText`），可带工具调用 | 按对话轮次 / 按 token | `ai_conversation` / `ai_message` |
| 图片 | 后台任务（Workflow；服务商可异步或同步产出） | 按生成次数 / 按张数（可按分辨率、步数加权） | `ai_task` + `file` |
| 视频 | 异步任务（Workflow + 服务商回调） | 按生成次数 / 按秒数（可按分辨率加权） | `ai_task` + `file` |

统一原则：
1. **先检查、再预扣、后调用**：权益（模型是否可用、并发数）→ 限流 → `credits.hold()` → 调用模型。
2. **产出落 R2**：服务商返回的 URL 会过期，结果一律转存 R2 并写 `file` 表。
3. **失败按类型结算**：文本最终失败且无可见正文时全额释放；有正文时按已产生用量计费，可通过模板配置改为所有失败全退；媒体失败释放预扣。未结算的 hold 由 Cron 兜底（见 05-billing「超时回收」）。
4. **文本出口由部署管理员选择**：Cloudflare 默认 AI Gateway/BYOK；Node 默认 OpenAI 兼容直连，可显式选择 Gateway。两出口使用同一预算与结算规则。

## 2. 模型注册表

`ai_model` 表（后台可编辑，KV 缓存）决定：模型对哪些套餐可见、走哪个 provider、如何计价、接受哪些参数。

### 计费方式

积分消耗支持三种计费方式，**按模型**在 `ai_model.pricing` 中选择——同一个站点可以让聊天按 token、视频按次，具体由站点的产品形态决定：

| 方式 | 适用 | 示例 | 预扣 | 结算 |
|---|---|---|---|---|
| `per_call` 按次 | 对话轮次、生成次数；价格对用户最直观 | 一轮对话 1 分；生成一个视频 5 分，1080p ×2 | 固定值 | 等于预扣，**不会超出** |
| `token` 按 token | 文本，成本随上下文和输出长度变化大 | 输入 2 分/1k，输出 8 分/1k | 估算上限 | 按实际 usage |
| `per_unit` 按用量单位 | 图片张数、视频秒数 | 每张 10 分；每秒 20 分 | 按请求参数计算 | 按服务商回报的 usage |

```ts
type Multipliers = Record<string, Record<string, number>>   // 参数名 → 取值 → 倍率，如 { resolution: { '720p': 1, '1080p': 2 } }

type Pricing =
  | {
      mode: 'per_call'
      credits: number                      // 每轮对话 / 每次生成的积分
      multipliers?: Multipliers            // 按请求参数加权，多个参数相乘
      chargeOn?: 'success' | 'any_output'  // 何时计费：媒体默认 success；文本默认 any_output（中断但已有输出也计费）
      limits?: { maxInputTokens?: number; maxOutputTokens?: number }  // 文本按轮计费时限制单轮成本上限
    }
  | { mode: 'token'; inputPer1k: number; outputPer1k: number; minCharge?: number }
  | { mode: 'per_unit'; unit: 'image' | 'second'; perUnit: number; multipliers?: Multipliers }

function estimateCredits(pricing, input): number   // 预扣用：per_call 为固定值，其余取上限
function actualCredits(pricing, usage): number     // 结算用：per_call 直接返回预扣值
```

- **按次计费的成本控制**：文本按轮计费时，平台的实际成本仍随上下文长度增长，必须配 `limits`（截断历史到 `maxInputTokens`、限制 `maxOutputTokens`），否则长会话会让单轮成本无上限。
- **默认值**：新建模型时的默认计费方式取 `template.config.ts` 的 `ai.defaultPricingMode`（如文本 `token`、图片和视频 `per_call`），后台可以逐个模型修改。
- **展示**：模型选择器与生成按钮旁显示本次预计消耗（按次直接显示固定值；按 token 显示「约 X–Y 分」）；用量页每条流水注明计费方式。

**定价快照**：`ai_model` 经 KV 缓存，后台改价后各地生效有延迟。为保证同一次调用的预扣与结算口径一致，发起调用时把当时的 `pricing` 写入 `ai_message.pricing` / `ai_task.pricing`，`estimateCredits` 与 `actualCredits` 都只读这份快照，不再重新读取 `ai_model`。改价只影响之后发起的调用。

`params_schema`（JSON Schema）用于：前端动态渲染参数表单、服务端校验输入，二者一致。

### 后台配置参数 schema

后台模型的新建、编辑和复制表单都提供 `params_schema` JSON 编辑框；必须输入 JSON 对象。文本模型可以填 `{}` 使用默认值，或配置 `x-text`。后台保存前使用共享的严格 schema 校验，拒绝未知键与非法值；已有非法文本配置在调用时整体降级为默认值。

| `params_schema['x-text']` 字段 | 类型 / 默认值 | 说明 |
|---|---|---|
| `tokensPerChar` | 正数 / `1` | 保守 token 估算系数 |
| `maxOutputTokens` | 正整数 / `4096` | 单次上游调用的输出上限 |
| `thinking` | 可选 boolean / 跟随 Provider adapter | 缺省由 adapter 决定是否可控；`false` 表示模型不支持，不下发、不允许用户切换；`true` 表示支持，但无 adapter 时仍忽略模板与请求的开关 |
| `continuation` | `native` 或 `none` / `none` | 是否允许 Provider 原生前缀续写；还须 Provider 实现该能力 |

媒体模型使用提交页和服务端共用的 `parseMediaSchema` 校验，只支持平面 `string`、`number`、`integer`、`boolean` 字段，以及枚举、范围、长度等现有约束；不支持嵌套对象。建议先通过「Insert reference template」填入 JSON，再按具体模型调整。模板覆盖当前编辑框内容，保存前应核对服务商和 `providerModelId`：

| 参考模板 | 服务商 / 适用 `providerModelId` | 参数 |
|---|---|---|
| Text · x-text defaults | 所有文本模型 | `tokensPerChar=1`、`maxOutputTokens=4096`、thinking 缺省（跟随 Provider adapter）、`continuation=none` |
| Workers AI · FLUX schnell | `workers-ai` / `@cf/black-forest-labs/flux-1-schnell` | `prompt` 长度 1–2048，`steps` 默认 4、上限 8；模板要求至少 1 步 |
| fal · FLUX schnell | `fal` / `fal-ai/flux/schnell` | `prompt`、`image_size` 六种尺寸枚举（默认 `landscape_4_3`） |
| fal · Wan v2.2 turbo | `fal` / `fal-ai/wan/v2.2-a14b/text-to-video/turbo` | `prompt`、`resolution`（`480p` / `580p` / `720p`，默认 `720p`）、`enable_prompt_expansion=false` |

参数名与取值以 [Workers AI FLUX schnell](https://developers.cloudflare.com/workers-ai/models/flux-1-schnell/) 和 [fal FLUX schnell](https://fal.ai/models/fal-ai/flux/schnell/api) 的官方文档为依据。fal 的自定义 `image_size` 对象不属于当前平面表单支持范围，参考模板使用官方枚举。模板是指定模型的起点，不能直接套用于同一服务商的任意模型。

Wan 模板遵循 [Wan v2.2 turbo 官方输入](https://fal.ai/models/fal-ai/wan/v2.2-a14b/text-to-video/turbo/api)，支持 [PR #93 录制请求](../packages/ai/src/media/fixtures/fal.recorded.json) 使用的 `prompt`、`resolution=480p`、`enable_prompt_expansion=false`；模板的分辨率默认值采用官方的 `720p`。该端点不支持 `duration`，模板不提供时长参数；此模板应配按次计费，不能把未提供的时长当作按秒计费依据。

保存后的 schema 用于未来提交的参数表单、校验和预算；已提交任务继续使用提交时校验后的参数与定价快照。创建和编辑的审计仅记录 `params_schema` 的哈希摘要（编辑含前后哈希），不保存完整 schema JSON。

## 3. 文本

### staging 故障模型的配置与权限

`AI_FAULT_INJECTION=enabled` 只允许显式 `SENTRY_ENVIRONMENT=staging`，由 web/jobs
的 Cloudflare 与 Node 环境装配校验。开关仅写在两个 Wrangler 文件的 staging vars；
缺失或 `disabled` 时正常模型保持原行为。production 配置任何该开关值（包括 `disabled`）、
未知环境开启或非法值均拒绝，错误仅报告变量名。

故障模型 key 必须以 `acceptance-fault-` 开头，并在 `params_schema` 顶层声明
`"x-acceptance-fault": { "mode": "fal-callback-lost" }`。媒体仍需完整的平面 schema；
扩展不会进入表单字段或 Provider 业务参数。合法模式限 Workers 的 `workers-error` /
`workers-timeout`（`workers-ai`、图片、`@cf/black-forest-labs/flux-1-schnell`），fal 的
`fal-callback-lost` / `fal-callback-early` / `fal-submit-response-lost` /
`fal-provider-error` / `fal-timeout`（图片、`fal-ai/flux/schnell`），以及文本的
`chat-before-stream` / `chat-mid-stream`（`deepseek`、`deepseek-flash`）。
前缀和元数据必须同时成立；不匹配或缺失时不能降级成普通模型。

故障列表与调用要求实时、未模拟的平台管理员会话；空间 owner/admin 与所有 API key 均无权限。
KV 保存完整注册表，每次读取后按环境和身份过滤，提交直接读库再次核验，仍执行原套餐权益、
余额、并发和限流。后台保存、复制、启用共用配置校验；复制不能去除故障标识，且副本先停用。
关闭闸门后仍可停用遗留模型，故障模型不可见、不可选。媒体提交冻结已接受任务的模式，
runner 每个持久步骤重新核验闸门，关闭后走失败结算释放预扣，禁止切换成真实普通调用或继续查询/取消。
故障模型由独立套件经后台创建、最终停用，
不写迁移种子，调用请求不能携带模式或时间策略。

### thinking、reasoning 与自动恢复

产品形态在 `template.config.ts` 配置，不由运行时设置覆盖：

| 配置项 | 默认值 | 行为 |
|---|---|---|
| `ai.text.enabled` | `true` | 是否启用文本对话 |
| `ai.text.thinking.default` | `'off'` | adapter 可控且模型未显式声明 `thinking=false` 时，默认显式下发关闭思考；可改为 `'on'` 显式开启 |
| `ai.text.thinking.userToggle` | `false` | 启用且 adapter 可控、模型未显式声明 `thinking=false` 时显示并接受逐条开关；关闭时携带请求 thinking 字段返回 400，启用但模型不可控时忽略该字段 |
| `ai.text.reasoning.display` | `false` | 开启时独立保存最终 attempt 的 reasoning 并折叠展示；关闭时不保存、不下发 |
| `ai.text.failedReplyRefund` | `'no-visible-output'` | 无可见正文的 failed 全退；`'all'` 为所有 failed 全退 |

只有非空 `text-delta` 算可见正文，reasoning 不算正文。正文出现前，瞬时错误（限流、5xx、网络与超时）、空回复与仅 reasoning 回复在同一预扣下最多重试 2 次，退避 1 秒 / 3 秒；展示 reasoning 时重试清空前一次思考并提示“重试中”。已有正文后流中断，模型声明 `continuation: 'native'` 且 Provider 支持时最多续写 2 次，正文追加到同一条消息。每 attempt 使用 `maxRetries: 0`，用户主动停止不触发自动恢复，超过 hold 截止时间不再重试。

当前仅 DeepSeek adapter 可控 thinking：统一 `reasoning` 参数配合 `providerOptions.deepseek.thinking.type=enabled|disabled`。模型 `params_schema` 为 `{}` 或未声明 `x-text.thinking` 时跟随 adapter，默认始终按模板或允许的请求值显式下发开/关；显式 `false` 时不下发、不允许用户切换。显式 `true` 也不能为其他 Provider 增加控制能力，无 adapter 时忽略开关并保持原行为。后台 Text 参考模板不填写 thinking 字段，跟随 adapter；已有模型的显式 `thinking=false` 继续禁用控制，后台严格校验保持不变。

已安装的 `@ai-sdk/deepseek@3.0.63` 原生支持末条 assistant 的 `providerOptions.deepseek.prefix=true`，SDK 将其映射为请求消息的 `prefix: true`。模型工厂仅为这类续写请求选择 `/beta` base URL（直连 `https://api.deepseek.com/beta`，Gateway 为 `/deepseek/beta`），普通请求沿用原端点，无需自定义 fetch/body 转换。此结论由本地 SDK 与假 fetch 测试核验，不代表已完成真实 Provider / staging 验收。

reasoning 仅以独立 `{ type: 'reasoning', text }` part 存储，永不进入历史上下文。后续请求包含 completed / aborted / failed 消息中的可见正文，包括失败前已生成的部分回复；`messageText` 只拼接 text part。API key completions 始终过滤 reasoning，不返回 `reasoning_content`。

### 文本计费矩阵

下表中的失败指重试或续写耗尽后的最终 failed；所有尝试共用一份 hold 与一条 assistant 消息。

| 最终状态 | `failedReplyRefund` | `token` | `per_call` |
|---|---|---|---|
| completed | 任意 | 最终成功 attempt 的输入 + 产生可见正文的各 attempt 输出（含其 reasoning） | 固定费用一次 |
| failed，无正文（含仅 reasoning） | 任意 | 全额释放 | 全额释放 |
| failed，有正文 | `'no-visible-output'` | 按已产生用量，封顶 hold | 默认 `any_output` 收固定费用一次；`success` 则释放 |
| failed，有正文 | `'all'` | 全额释放 | 全额释放 |
| aborted，用户主动停止 | 任意 | 沿用已产生用量的估算，封顶 hold | 沿用 `chargeOn`：默认有正文收费，否则释放 |

`reasoningTokens` 单独记录，同时属于 `outputTokens`，不能再重复相加收费。检查点 JSON 的 `total` 记录所有 attempt 的累计输入、输出和 reasoning 用量；正文前被丢弃的 attempt 另记 `absorbed`，成本由 SaaS 承担，不计入用户扣费。检查点包含 reasoning 的估算 token；正文前重试时重置被丢弃 attempt 的检查点贡献。超时回收同样先判断持久化正文：没有正文即全退，有正文时按最后检查点结算且封顶 hold；`failedReplyRefund='all'` 也适用于回收失败。

### Gateway 与密钥

部署管理员通过 `AI_TEXT_EGRESS=direct|gateway` 选择出口，非法值校验失败。Cloudflare 缺省为
`gateway`，Node schema 缺省为 `direct`，Node composition 应原样注入这项配置。
模型后台只管理 provider、模型 ID、参数和定价，没有端点或密钥列；本轮无 schema 变更。

直连时，在部署 env 配置 `OPENAI_BASE_URL`（完整 HTTP(S) API base，如 `https://compatible.example/v1`）
和 `OPENAI_API_KEY`，Node 也可用 `OPENAI_API_KEY_FILE` 挂载 secret；直接值与 `_FILE` 不能同时提供。
后台文本模型 provider 填 `openai`，Provider model ID 填兼容服务接受的模型 ID。
URL 不接受内嵌用户名/密码、query 或 fragment；普通聊天请求不能指定端点。直连不要求 Gateway
配置、不发送 `cf-aig-*` 头，不读取 SDK 的隐式进程密钥；缺少管理员 key 时在预扣前返回 503。
`deepseek` 例外：Cloudflare AI Gateway 会把 DeepSeek 的 SSE 整段缓冲到生成结束才返回
（2026-10-13 实测 `/deepseek` 与 `/compat` 端点、BYOK 或显式密钥、跳过缓存与日志均如此，
同一 Gateway 的 Workers AI 正常逐块；见 issue #152），用户只能看到一次性到达的回复。
因此 `AI_TEXT_EGRESS=direct` 且配置了 `DEEPSEEK_API_KEY` 时，DeepSeek 直连官方
`https://api.deepseek.com`，不发送 `cf-aig-*` 头；未配置该密钥时仍走下面的 Gateway（BYOK）路径。
需要逐步显示回复的 Cloudflare 部署应设置 `AI_TEXT_EGRESS=direct` var 与 `DEEPSEEK_API_KEY` secret
（此时 `openai` 模型也按上文要求 `OPENAI_BASE_URL`）。
其他原生 provider 保持下面的 Gateway 路径，`AI_TEXT_EGRESS` 不为它们新增直连协议。

文本调用有两种密钥存放方式，均经 `https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}` 转发：

- **默认 BYOK**：在 Cloudflare AI Gateway 的 **Provider Keys** 为所用服务商保存 API Key（使用 `default` alias），开启 Gateway 鉴权。Worker 只需 `AI_GATEWAY_TOKEN` secret 与 `AI_GATEWAY_ACCOUNT_ID` / `AI_GATEWAY_ID` vars；请求不发送 Provider 授权头，由 Gateway 注入所存密钥。SDK 所需的占位 API Key 不能出现在最终请求的 Provider 授权头中，否则 Gateway 会转发占位值而不会使用 BYOK。见 [Cloudflare BYOK](https://developers.cloudflare.com/ai-gateway/configuration/bring-your-own-keys/)。
- **可选 Worker secrets**：把所用 Provider 的 API Key 存为 Worker secret，本地写入 app `.dev.vars`；模型工厂按服务商发送对应授权头，经 Gateway 转发给 Provider。支持 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`、`GOOGLE_API_KEY`、`DEEPSEEK_API_KEY`；显式提供的 Provider 密钥优先于 Gateway 中的 BYOK。

`AI_GATEWAY_TOKEN` 用于 Gateway 鉴权，请求头为 `cf-aig-authorization: Bearer <AI_GATEWAY_TOKEN>`，与 Provider 授权分开；token 需有 Cloudflare **AI Gateway Run** 权限。见 [Authenticated Gateway](https://developers.cloudflare.com/ai-gateway/configuration/authentication/)。Provider 路径与可选密钥映射如下：

| Provider | Gateway 路径（接在上述前缀后） | 可选 Worker secret | Provider 授权头 |
|---|---|---|---|
| [OpenAI](https://developers.cloudflare.com/ai-gateway/usage/providers/openai/) | `/openai` | `OPENAI_API_KEY` | `Authorization: Bearer <key>` |
| [Anthropic](https://developers.cloudflare.com/ai-gateway/usage/providers/anthropic/) | `/anthropic`（消息接口 `/v1/messages`） | `ANTHROPIC_API_KEY` | `x-api-key: <key>` |
| [Google AI Studio](https://developers.cloudflare.com/ai-gateway/usage/providers/google-ai-studio/) | `/google-ai-studio`（SDK 使用 `/v1beta`） | `GOOGLE_API_KEY` | `x-goog-api-key: <key>` |
| [DeepSeek](https://developers.cloudflare.com/ai-gateway/usage/providers/deepseek/) | `/deepseek` | `DEEPSEEK_API_KEY` | `Authorization: Bearer <key>` |

本地注入与线上 secret 配置见 [基础设施 §4](./07-infrastructure.md#4-环境变量与绑定清单)。根 `.env.local` 的默认 dev 支付同步不加载 AI 密钥。2026-10-12 已用默认模型工厂与 AI SDK 的 `generateText`、`streamText` 对 DeepSeek `deepseek-flash` 分别完成本地真实调用：仅传 Gateway 配置，使用托管密钥（BYOK），未传 `DEEPSEEK_API_KEY`，均回复 `OK.`，usage 为输入 7 / 输出 2 tokens。中断流日志回查仍因缺少 AI Gateway 日志读取权限的 token 阻塞，详见 change design 的 Open Questions；这次验证不替代 staging 计费验收。

### 流程

staging 文本故障在正常模型工厂产生的 `doStream` 外包装，不在预扣前的构造阶段抛错。
模式在 fresh 管理员 gate 后冻结；assistant 初始检查点保留预算输入估算、0 输出及
`acceptanceFaultProof`（版本、mode、phase、injected、realProviderCalled、upstreamCalls）。
正常 token 检查点与证明使用局部 JSON 合并，结算保留证明；实际进入注入分支且证明写入成功后，
才能记 `injected=true`。上游自然错误、输出未达到阈值或证明写入失败不能认证故障注入成功。

| 模式 × 定价 | 上游与输出 | 结算预期（默认失败退款口径） |
|---|---|---|
| `chat-before-stream` × `per_call` | 不调用上游，无 assistant 输出 | failed、全额释放、0 消费 |
| `chat-before-stream` × `token` | 不调用上游，无输出；保留预算输入估算 | failed、全额释放、0 消费 |
| `chat-mid-stream` × `per_call` | 调用上游一次，转发到至少200估算输出 token 后流异常 | 保留真实部分回复，failed、固定费用消费一次 |
| `chat-mid-stream` × `token` | 同上，用原模型 tokensPerChar 估算 | failed、按已产生用量/minCharge 精确计算并封顶 hold，无额外补扣、欠费或超额承担 |

所有文本 attempt 均设置 `maxRetries=0`，故障调用的输出上限最多1024。流中注入取消上游 reader，通过
`controller.error` 结束，不能只发送 error chunk 再 close，也不触发业务“用户停止”控制器；
异常不会被 onEnd 认证成 completed。独立本地假上游仍经过该包装器；未知 Provider/model ID
明确拒绝，不回退真实服务商。流前证明是合成错误，流中才包含上游实际调用及部分文本的业务证据；
本地夹具不作为真实 staging 或 Gateway token 差异证据。

```
1. 解析会话、校验模型可用；取定价快照 pricing
2. 计算预扣额与 maxOut：
   per_call：amount = credits × multipliers；按 limits 截断历史，maxOut = limits.maxOutputTokens ?? 模型上限
   token：   inputCost = inputTokens(字符估算) * inputPer1k / 1000
             maxOut = min(模型/请求的 maxOutputTokens, floor((balance - inputCost) * 1000 / outputPer1k))
             outputPer1k=0 时不按余额收缩输出，仍校验输入费用与最低费用
             若 maxOut < minOutputTokens（默认 256）或余额不够 minCharge → INSUFFICIENT_CREDITS
             amount = max(ceil(inputCost + maxOut * outputPer1k / 1000), minCharge ?? 1)
3. hold(amount)                                     // expires_at = now + 10min
   插入 assistant message（status='streaming', hold_id）
4. 在同一 hold 下编排 streamText attempts（maxRetries: 0），按上述规则重试或续写
5. ctx.waitUntil(done)                              // done 包含 consumeStream、等待检查点写入、结算
   onChunk 收到新正文或 reasoning 时：每 5 秒或新增 200 个估算输出 token 写 usage_checkpoint 与已生成内容
6. 保存合并正文与 usage；开启展示时保存最终 attempt 的 reasoning；读流及检查点写入完成后：
   正常结束 → 按上述矩阵结算；缺失 usage 时按封顶估算结算 → completed
   最终失败 → 无正文或 failedReplyRefund='all'：release；否则按部分用量结算 → failed
   用户停止 → 沿用按已产生用量 / chargeOn 的规则，金额不超过 hold.amount → aborted
```

- **按余额压低 `maxOutputTokens`**（仅 token 计费）：按模型上限全额预扣，会让余额不多的用户连短对话都发不出去；改为按余额计算本次可用的最大输出，余额只够很短的回复时才拒绝。
- **输入 token 估算**：`packages/ai/src/text/budget.ts` 按 Unicode 码点计数，每条消息为 `8 + ceil(字符数 × tokensPerChar)`，所有消息相加；默认系数 `tokensPerChar=1`。模型可在 `ai_model.params_schema['x-text']` 配置正数系数与 `maxOutputTokens`（默认 4096），缺失或配置不合法时使用默认值；首版没有调用服务商计数接口。按次文本模型从最早的历史开始丢弃，直到估算输入符合 `limits.maxInputTokens`；最后一条消息仍超限时返回 `INPUT_TOO_LONG`。估算用于预算与中断兜底，不是服务商的精确分词结果；输入低估可能导致真实 usage 费用超过预扣，按 05-billing「超额容忍」处理。正常完成优先使用 AI SDK 的最终输入 / 输出 usage，缺失的字段分别回退为输入估算 / 最终文本估算；只要使用了估算，结算金额就不超过预扣额。
- **客户端中断后的结算**（平台行为见下方 Phase 0「实测记录」）：第 5 步把服务端读流、等待检查点写入和结算一起放入 `waitUntil`；用户关闭页面后服务端仍继续读流。模型在**断开后 30 秒内**输出完毕时，`onEnd` 保存最终 usage，随后结算并保存完整回复（被中断的回复仍按完整输出计费）。客户端保持连接时不受这个断开后的 30 秒时限约束。显式停止使用 `POST /api/ai/chat/:messageId/stop`：同一 isolate 中 abort 上游，按内存中的已生成文本估算结算；其他 isolate 按已持久化的最后一个检查点结算，原读取器在下次写检查点时发现消息已结束后 abort。停止回复标记为 `aborted`。
- **兜底**：Phase 0 实测 `waitUntil` 的时限是**客户端断开（或响应结束）后 30 秒**。超时后运行时直接取消剩余任务（日志：`waitUntil() tasks did not complete within the allowed time after invocation end and have been cancelled`），结束回调、`catch` / `finally` 不会执行，回复可能丢失结算。对话 hold 的有效期为 10 分钟，过期后由 Jobs 的 `ai_message` 回收处理器结算。
  - **用量检查点**：`onChunk` 收到新文本或 reasoning 时判断距上次检查点是否已过 5 秒，或新增估算输出是否达到 200 token，先到者触发；没有新输出时不写入。写入串行、不阻塞读流，把 `{inputTokens, outputTokens, reasoningTokens, absorbed, total, at}` 与截至检查点的正文一起保存（仅开启展示时另存 reasoning part），只更新 `streaming` 消息；写入失败只记日志。输入沿用发起时的估算，输出包括正文与 reasoning 的估算，reasoning 另记 `reasoningTokens`。检查点只保存了部分文本，估算 token 数可能高于服务商实际分词数（英文尤其明显），按检查点结算以预扣额封顶；封顶不等于精确用量，仍需通过最终 usage 与估算的差异校准模型系数。正常完成时检查点不参与结算金额。
  - **最低费用（Q7）**：结算丢失时，回收按 failed 口径：无持久化正文（即使检查点已有 reasoning 输出）或开启所有失败全退时，全额释放。有正文时，按 token 使用最后一个检查点的输入 / 输出用量，金额为 `min(max(ceil((inputTokens × inputPer1k + outputTokens × outputPer1k) / 1000), minCharge ?? 1), hold.amount)`；按次默认 `any_output` 收取固定费用，`success` 则释放。回收处理器把消息标为 `failed`，保留截至最后检查点的部分回复；结算和消息更新在同一事务内，通过 hold 状态避免重复结算。
  - 未采纳：断开约 25 秒后主动中止生成——会截断用户的回复，且中止后服务商不一定返回 usage。代价是断开超过 30 秒后服务商仍在生成的那部分输出平台无法收费，作为已接受的取舍，通过监控被取消的回复数量评估；影响明显时再考虑主动中止，或由 Durable Object 承载超长生成。
  - 观测注意：客户端断开的请求在 Workers Logs / `wrangler tail` 中的 `outcome` 为 `canceled`，即使 `waitUntil` 中的结算已成功完成；判断是否结算要看 `ai_message.status`，不能看请求的 `outcome`。

> **实测记录（tasks 7.3，2026-10-03，wrangler 4.146，compatibility_date 2026-10-01）**：临时 Worker 产生每 500 ms 一块的模拟模型流，`tee()` 一路作为响应、另一路在 `ctx.waitUntil` 中读完，读流期间每 5 秒、读完时各写一行 `setting`（经阶段一 staging 的 Hyperdrive）；客户端在约 6 秒时主动断开。代码与复现步骤见 `scripts/probes/stream-7_3/`。
>
> | 场景 | 断开（或响应结束）后源流还需 | 服务端读到 / 应有块数 | 读完并写库 | 最后一次写库（距请求开始） |
> |---|---|---|---|---|
> | 不断开（基线） | — | 40 / 40 | 是 | 20 s |
> | `waitUntil`，断开 | 约 9 s | 30 / 30 | 是（2 次） | 15.2 s、15.3 s |
> | `waitUntil`，断开 | 约 29 s | 70 / 70 | 是（2 次） | 35.8 s、36.0 s |
> | `waitUntil`，断开 | 约 59 s / 119 s / 299 s | 71 / 130、71 / 250、71 / 610 | 否（4 次均在断开后约 30 s 被取消） | 36.3–36.6 s |
> | 不用 `waitUntil`（对照），断开 | 约 29 s | 11 / 70 | 否（断开即停止） | 5.5 s |
> | 立即返回短响应，只在 `waitUntil` 中读流 | 10 s / 30 s | 全部 | 是 | 10 s、30 s |
> | 同上 | 60 s / 120 s | 47 / 120、51 / 240 | 否（响应结束后约 30 s 被取消，请求 wallTime 约 30.5 s） | 26 s、25.5 s |
>
> 结论：`waitUntil(consumeStream())` 能让断开后的读流与写库继续进行，时限为断开或响应结束后 30 秒，超过即被静默取消。

**对话断连回归用例（tasks 2.7）**：见 [`apps/web/e2e/ai-chat-disconnect.spec.ts`](../apps/web/e2e/ai-chat-disconnect.spec.ts)。用例通过仅 e2e 使用的 Vite 模型注入运行实际聊天接口与结算：短流在输出过程中关闭页面，重新打开后检查完整回复与完整 usage 费用；长流在关闭页面后超过 30 秒并保持挂起，直接运行实际 hold 回收器，检查部分回复、检查点费用、积分流水和对账不变式。本地 Miniflare 不会复现平台在 30 秒后的静默取消，这一长流用例验证检查点持久化与回收结算；平台取消行为的依据仍是上方 Phase 0 部署实测。真实 AI Gateway / 服务商用量对比与 staging 验收另见 tasks 2.1、5.1。

在已应用迁移的独立 Orca worktree 中运行 `pnpm --filter @product-res/web exec playwright test -c playwright.disconnect.config.ts`。长流用例只在事务中调用当前 hold 的真实 `chatHoldSweeper`（模拟到期），避免全库快进回收影响其他测试预扣；重复触发须被账本拒绝，且只产生一条消费流水。不要与类型检查、构建或集成测试同时运行，以免共用生成产物或数据库状态相互影响。

- **估算结算封顶（tasks 2.8）**：停止（同一 isolate 的内存估算或跨 isolate 的检查点）、出错和超时兜底都以 `min(估算金额, hold.amount)` 结算；`minCharge` 下限先应用，再受预扣额封顶。这些路径不触发超额容忍、不补扣余额、不产生欠费。结算入口显式区分真实 usage 与估算，为 tasks 2.9 取回实际用量保留入口；当前尚未实现 AI Gateway 用量回查。
- 服务商报告的真实 usage 费用超过预扣时，**不中断生成**，输出完成后按 05-billing「超额容忍」结算：额度内由平台承担，超出额度的部分从余额补扣，余额不足记为欠费。
- 上下文管理：按模型 context window 截断历史；长会话可做摘要（后续）。

## 4. 图片 / 视频：异步任务

### 服务商注册表与接口

模型注册表 `ai_model` 负责模型参数、套餐可见性和计价；[媒体服务商注册表](../packages/ai/src/media/registry.ts)负责执行能力。`ai_model.provider` 对应定义的 `id`，定义包括 `synchronous`、`supportedKinds`、`outputHosts`、`isConfigured(env)` 与 `create(env, { modelId })`。任务保存服务商与 `providerModelId` 快照，运行时按快照重建实例，不依赖 isolate 内的作业映射。

| 服务商 ID | 能力 | 配置检查 | 产出与下载白名单 |
|---|---|---|---|
| `fal` | 异步图片 / 视频 | `FAL_KEY` | HTTPS URL；精确主机 `fal.media`、`v3.fal.media`、`v3b.fal.media` |
| `workers-ai` | 同步图片 | `AI` 绑定 | 图片字节；`outputHosts=[]`，无需外部下载 |

`template.config.ts` 的 `ai.mediaProviders` 默认启用 `['fal', 'workers-ai']`。提交入口在创建任务和预扣前拒绝未注册、未启用、未配置或不支持该媒体种类的服务商；异步服务商还须配置 `MEDIA_WEBHOOK_SECRET`。后台媒体模型表单按启用列表提供服务商选项；回调入口对未知或同步服务商返回 404。通用运行时、提交校验、回调与转存白名单均查同一注册表。

接口的完整类型见 [provider.ts](../packages/ai/src/media/provider.ts)：

```ts
interface MediaSubmitInput {
  modelId: string
  params: Record<string, unknown>
  webhookUrl?: string
  idempotencyKey: string // ai_task.provider_request_key；不支持时实现方忽略
}

interface MediaProvider {
  readonly id: string
  readonly capabilities: { readonly idempotentSubmit: boolean }
  submit(input: MediaSubmitInput): Promise<{ jobId: string; sync?: MediaResult }>
  getStatus(jobId: string): Promise<MediaStatus>
  parseWebhook(req: Request, rawBody: string): Promise<MediaWebhook>
  cancel?(jobId: string): Promise<void>
}

interface SyncMediaProvider {
  readonly id: string
  readonly capabilities: { readonly synchronous: true; readonly idempotentSubmit: boolean }
  run(input: MediaSubmitInput): Promise<MediaBinaryResult>
}

type TaskMediaProvider = MediaProvider | SyncMediaProvider
```

`MediaResult` 包含下载地址、MIME、可选宽高 / 视频时长，以及可选 `usage.images` / `usage.seconds`；`MediaStatus` 为 queued / running / succeeded（带结果）/ failed（带错误）。`MediaWebhook` 始终带 `jobId`，可以带结果、错误或仅通知查询原作业。同步 `MediaBinaryResult` 的输出为 `Uint8Array` / `ReadableStream<Uint8Array>` 与 MIME，不能作为 Workflow step 返回值。

### fal.ai 实测与能力标记

[Queue](https://fal.ai/docs/documentation/model-apis/inference/queue) 和[请求头](https://fal.ai/docs/documentation/model-apis/common-parameters)文档没有承诺客户端提交去重。**2026-10-12（Asia/Taipei）实测**：向 `fal-ai/flux/schnell` 连续发送完全相同的请求体与同一个 `Idempotency-Key`，返回两个不同的 `request_id`，主动查询确认两个作业都完成。因此该端点在本次测试中未按此请求头去重；这不证明任何其他未测试机制均无效，但不足以承诺安全重提，当前继续设 `idempotentSubmit=false`，实现忽略提交键且不自动重试。

真实录制见 [夹具与录制说明](../packages/ai/src/media/fixtures/README.md)：提交 HTTP 200；运行状态 HTTP 202 且 `logs=null`；完成与图片结果 HTTP 200；成功回调 `status='OK'` 且 `error=null`。回调通过临时接收器取得，原始请求体在脱敏前用 fal 公开 JWKS 验证 Ed25519 签名；离线测试对脱敏后的真实载荷重新签名，不能把测试签名称为 fal 原签名。两个 512×512 图片及一次 480p 视频提交按公开价格保守估算最多 $0.056，未部署 staging。

视频仅提交后立即 PUT 取消，返回 HTTP 202 `CANCELLATION_REQUESTED`；取消后的即时查询仍为 `IN_PROGRESS`，未获取视频结果。202 只代表接受取消请求，不保证已停止推理或免费；已完成图片的取消实测返回 HTTP 400 `ALREADY_COMPLETED`。视频结果、生成失败与异常回调仍由官方文档构造的补充夹具覆盖，不作为真实录制证据。

`createFalMediaProvider({ apiKey, modelId, fetch })` 按任务模型创建实例，查询 / 取消使用原始 `request_id`，队列路径按基础模型去掉子路径。`FalProviderError.submissionOutcome` 区分明确拒绝与可能已受理。回调按[官方验签协议](https://fal.ai/docs/documentation/model-apis/inference/webhooks)验证 Ed25519、原始请求体 SHA-256 与 ±5 分钟时间窗，JWKS 最多缓存 24 小时；`payload_error` 通知只返回 `jobId`，调用方查询原作业。视频未回报时长时不提供 `usage.seconds`，不能用推理耗时计费。

### Workers AI 同步产出路径

[Workers AI Provider](../packages/ai/src/media/workers-ai.ts) 通过 `AI.run(providerModelId, params)` 调用图片模型：Flux 的 base64 与 SDXL 等模型的二进制流都根据文件头识别 JPEG / PNG / WebP / GIF，返回一张图片的用量。web / jobs 均声明 `AI` 绑定，web 用它检查是否已配置，实际推理由 jobs 执行；无外部密钥，费用计入 Cloudflare 账号。

用户仍通过同一个任务接口立即获得 `taskId`。Workflow 的 `submit` step 调用 `run` 后，在**同一个 step** 内按确定性 R2 key 写对象与 `file` 记录，并保存结果和用量，只返回文件 ID，然后直接进入 `settle-and-notify`；不进入回调、等待或轮询。同步提交 step 超时 15 分钟；只有 Provider 标为瞬时的失败（Workers AI 官方错误码 3007 超时、3008 中止、3040 容量不足）按 10 秒起指数退避最多重试 2 次，其余失败以 `NonRetryableError` 带原错误码立即终止，最终失败全额释放。绑定错误只保留错误名与数字码（如 `AiError 8007`）写入任务错误信息与 `ai.media.sync_submit_failed` 日志，上游描述可能回显提示词，不保留。8007（输入被判定为 NSFW）不重试：2026-10-13 实测同一无害提示词在 REST API 上时而成功时而 8007，但重试内容审核拒绝等同绕过审核。重放可能重新推理，但覆盖同一对象并复用文件记录，不重复文件或积分结算；`idempotentSubmit=false` 不代表推理本身可去重。转存同样检查 MIME、单文件大小和空间配额，字节不会跨 step 传递。


### Workflow

[ai-media.ts](../apps/jobs/src/workflows/ai-media.ts)负责绑定、Provider 创建和存储依赖，[media-runner.ts](../apps/jobs/src/workflows/media-runner.ts)执行持久步骤。异步流程为：

```text
load-task → submit → check-callback
  → 若无结果：wait-media-done → recheck-callback → poll-N / poll-delay-N
  → persist → settle-and-notify
失败 → fail-and-notify；已终态 → 停止后续业务步骤
```

- **提交幂等**：创建任务时 `provider_request_key=task.id`，Workflow 实例 ID 也为 `task.id`。`submit` 先读库，已有 `provider_job_id` 直接复用；外部调用前持久化 `output.submissionAttempted`，防止非幂等服务商在受理与 jobId 落库之间崩溃后再次提交。拿到 jobId 立即落库并置 running。明确拒绝会清除此标记，允许 step 重试；不支持幂等时的超时、连接中断、5xx 或响应丢失会变为 `NonRetryableError('MEDIA_SUBMISSION_UNCERTAIN')`，任务失败退款。
- **回调与事件**：保留 `check-callback` 与 `recheck-callback`。`sendEvent` 的 `{ taskId }` 只唤醒 Workflow，结果始终重新读取已落库的 `callback_payload`；通知失败也能在等待超时后恢复。已收到仅含 jobId 的通知时直接查询原作业，不再等满 15 分钟。
- **转存 R2**：使用确定性 key `ws/{workspaceId}/ai/{taskId}/{输出序号}`，重放覆盖同一对象并复用文件记录。带 `Content-Length` 时经 `FixedLengthStream` 流式写入；无长度时用 multipart（除最后一片外每片至少 5 MB），累计超上限即中止。限制类型与精确主机白名单，单文件上限为 100 MiB，并检查提交时与当前权益的空间配额。
- **结算与终态**：成功按任务定价快照结算，媒体用量以请求参数上限封顶；失败 / 取消全额释放。结算与站内通知使用共用 `settleMediaTask`；每个步骤前及缓存步骤返回后自检终态，晚到 Workflow 不重复扣费。

### 等待与轮询参数

合法故障任务把版本 1 固定策略及管理员授权结果存入 `input.acceptanceFault`，后续修改或停用
模型不改变原任务。执行证明放在独立的 `input.acceptanceFaultProof`，空间→任务锁下局部合并，
不进入 Provider 参数，也不依赖结算时覆盖的 output。fal 专用输入固定 square、一张；所有 hold
仍在 deadline 后 10 分钟到期，正常任务的 2 小时 deadline、15 分钟等待及重试参数保持。

| 故障模式 | 固定时间与触发方式 | 证据边界与结果 |
|---|---|---|
| `workers-error` | 合成不可重试 `WORKERS_AI_GENERATION_FAILED` | 不调用 AI 绑定，不产生字节/文件；failed、全退 |
| `workers-timeout` | 60 秒 deadline；running 状态持久 sleep 至 deadline，再由 active 检查超时 | 不调用 AI，不伪造图片或直接结算；证明任务截止与退款，不声称真实服务挂起 |
| `fal-callback-lost` | 20 分钟 deadline；真实 submit 去掉 webhook；wait 5 秒后查询原作业 | 一次真实 submit、真实 request ID、pollCount>0、无 callback；成功产出与消费各一份 |
| `fal-callback-early` | 20 分钟 deadline；真实 webhook；jobId 落库后在正常 check 前最多等 10 分钟，每 2 秒持久 sleep | 验签回调先落库，再记录 callbackCheckedAt；未观察到则失败，不能用普通轮询成功代替 |
| `fal-submit-response-lost` | 真实 submit 去掉 webhook；ID 写证明后抛 ambiguous 错误 | 业务 jobId 留空，原 UNCERTAIN 全退且不重提；证明 ID 结算后仍存在 |
| `fal-provider-error` | 20 分钟 deadline、wait 5 秒；查询真实原作业后包装成确定失败 | 原失败全退；真实成功回调经验签后被忽略，不能恢复成功 |
| `fal-timeout` | 60 秒 deadline、wait 5 秒；查询真实原作业后包装 queued，睡眠截短到剩余 deadline | 实际到 deadline 才超时全退，不能产出图片；晚到结果/重放不重复结算 |

三个失败 fal 模式按证明中的原 request ID 尽力取消，记录 `cancellation-requested`（仅受理）、
`already-terminal`（取消失败后原 Provider 查询已 succeeded/failed）或 `unconfirmed`。
202 不证明推理已经停止，也不免除服务商计费；仍 queued/running、取消与查询失败均需人工核验，
不能重提来补证据。终态回调与 Workflow 重放沿用原结算幂等，证明保留且只生成一份通知。

错误码沿原结算路径：Workers 使用原 `WORKERS_AI_GENERATION_FAILED`，fal 响应丢失为
`MEDIA_SUBMISSION_UNCERTAIN`，确定失败为 `FAL_GENERATION_FAILED`，deadline 为 `MEDIA_TIMEOUT`。
Cloudflare step 会序列化异常，自定义 code 可能丢失后落到 `MEDIA_GENERATION_FAILED`；验收必须记录
实际安全码，并用持久注入证明、终态与积分判定，不能把本地中立异常码假定为部署结果。

| 位置 | 当前参数 | 停止条件 |
|---|---|---|
| Workflow 回调等待 | 最多 15 分钟，且不超过剩余硬超时 | 事件唤醒或等待超时后重新查库 |
| Workflow 主动查询 | 进入轮询先查一次；随后间隔 30、60、120、240、300 秒，之后保持 300 秒；每次查询一个 `step.do`，间隔一个 `step.sleep`，睡眠不超过剩余截止时间 | 成功 / 失败 / 取消，或到达 `deadline_at` |
| 任务硬超时 | 创建时起 2 小时；hold 到期为 `deadline_at + 10 分钟` | Workflow 超时失败退款；DB-only hold 回收器补结算或将未终态任务标为 `MEDIA_DEADLINE_EXCEEDED` 并释放 |
| 前端详情 / 列表 | 首次立即读取；间隔 2、4、8、10 秒，之后保持 10 秒 | `succeeded` / `failed` / `canceled` 后停止；页面隐藏时中止请求，恢复可见时立即读取并重置间隔，终态仅手动刷新 |
| 异步 submit / persist step | 均最多重试 3 次，10 秒起指数退避；超时分别 2 分钟 / 15 分钟 | 不确定的非幂等提交不重试；同步 submit 的参数见上节 |

前端轮询实现见 [polling.ts](../apps/web/src/features/ai-media/polling.ts)；任务 TTL 与回收缓冲见 [tasks.ts](../packages/ai/src/media/tasks.ts)。回收器只读写数据库，不在事务中查询 / 终止 Workflow 或取消外部作业；Workflow 发现终态后尽力取消外部作业并退出。

> **`waitForEvent` / `sendEvent` 实测（Phase 0 任务 7.2，2026-10-03，wrangler 4.146，compatibility_date 2026-10-01）**
>
> **方法**：部署一对临时 Worker（`scripts/probes/72-workflow/`，测完已删除）：`probe-72-workflow` 定义 Workflow `probe-72-wf`（先 `step.sleep(N)`，再依次 `waitForEvent`，超时被捕获并写入输出）；`probe-72-caller` 经 `script_name` 绑定它，模拟 web → jobs。由 `run.mjs` 驱动各场景，读取实例 `status()` 的 `output` 判断事件是否、何时被投递。
>
> **结果**（原始输出摘录，时间为 Workflow 内 `step.do` 记录的毫秒时间戳）：
>
> | 场景 | 操作 | 结果 |
> |---|---|---|
> | 跨 Worker 基线 | caller `create()`（返回时 `queued`）→ 实例进入 `waitForEvent` 约 12 s 后 `sendEvent` | 送达，发送后约 30 ms 投递，`payload` 原样收到 |
> | 实例尚未开始执行 | 同一次调用中 `create()` 后立即 `sendEvent`（发送时实例状态为 `queued`） | 送达；实例开始后进入 `waitForEvent` 立即拿到事件 |
> | 实例在 `step.sleep(30s)` 中 | 创建后约 6 s 发送，约 26 s 后才进入 `waitForEvent` | 送达；`event.timestamp` 为发送时间，而不是进入等待的时间 |
> | 保留时长 | 创建后立即发送，分别 `step.sleep` 60 s / 5 min / 15 min / 60 min 后进入 `waitForEvent` | 4 个实例全部送达：发送到进入 `waitForEvent` 的间隔分别为 62.5 s、305.8 s、902.5 s、3600.7 s，进入等待后 40–112 ms 拿到事件 |
> | 多个事件先到 | 先发 `a#1`、`a#2`、`b#3`、`other#4`；再依次等 `b`、`a`、`a`、`a(15s)` | 依次收到 `#3`、`#1`、`#2`，最后一个 `a` 超时：按 type 匹配，同 type 先进先出，每个事件只被消费一次；未被等待的 `other` 不影响其他 type |
> | type 含 `.` | `sendEvent({ type: 'media.done' })`；`waitForEvent({ type: 'media.done' })` | `sendEvent` 抛 `(workflow.invalid_event_type) Provided event type is invalid`；`waitForEvent` 不报错，但永远收不到，直到超时。改用 `media-done` 正常 |
> | 实例已结束 | 对 `complete` 的实例 `sendEvent` | 抛 `(instance.in_finite_state) Instance reached a finite state, cannot send events to it` |
> | 实例不存在 | `get(id)` | 抛 `(instance.not_found) Instance not found` |
> | 等待超时 | `waitForEvent` 到达 `timeout` | 抛 `Error: Execution timed out after <ms>ms`，可被 `try/catch` 捕获，实例继续执行并正常 `complete` |
>
> 其他观察：短时间的 `step.sleep` / `waitForEvent`（几十秒内）期间 `status()` 返回 `running`；60 分钟的 `step.sleep` 在进行约 15 分钟时返回 `waiting`。状态不能用来判断实例是否已执行到 `waitForEvent`（也不需要，见结论 2）。`wrangler delete` 删除 Worker 不会删除其中定义的 Workflow，需另外执行 `wrangler workflows delete <name>`。
>
> **结论**：
> 1. 跨 Worker（`script_name` 绑定）的 `create`、`get`、`status`、`sendEvent` 均可用，与在定义 Workflow 的 Worker 内调用无差别。
> 2. 实例存在之后（含 `queued`、尚未执行、`step.sleep` 中）发出的事件会被**保留**，之后执行到匹配 type 的 `waitForEvent` 时立即投递；实测至少保留 60 分钟（发送后 3600.7 s 仍送达；更长时长未测；已覆盖媒体任务 `waitForEvent` 的 15 分钟超时）。官方文档的表述一致（事件会被缓冲，直到实例执行到匹配的 `waitForEvent`），但没有给出保留上限。
> 3. 事件类型只能用 `^[a-zA-Z0-9_][a-zA-Z0-9-_]*$`（文档如此，实测 `.` 被拒）。`waitForEvent` 端写错 type 不会报错，只会一直等到超时。
>
> **本 change 已采纳的结论**（原探针与复现说明见 [Phase 0 任务 7.2](../scripts/probes/72-workflow/README.md)）：
> - 事件早到时平台会缓冲，至少 60 分钟后仍可送达；这是 Phase 0 实测结论，本轮 fal 录制不重新证明平台事件保留上限。
> - 两端共享 `MEDIA_DONE_EVENT='media-done'`，不用含 `.` 的类型；Workflow 实例 ID 固定为 `task.id`，创建实例后才提交服务商。
> - 保留设计决策 3 的 `check-callback` 与 `recheck-callback`：缓冲能处理早到事件，数据库仍是结果事实来源；先落库后 `sendEvent` 失败时，提前检查可避免无谓等待，超时后检查可恢复结果。事件只用于唤醒，不直接结算其 payload。

### 回调入口
`POST /api/webhooks/media/:provider?task=:id&sig=:hmac`
- 用自签 HMAC（taskId + secret）校验 URL，外加 provider 自身的签名校验（如有）。
- **先落库，再通知**：把解析后的结果写入 `ai_task.callback_payload`（仅当为空时写入，幂等），再 `env.AI_MEDIA_WORKFLOW.get(ai_task.workflow_instance_id).sendEvent({ type: MEDIA_DONE_EVENT, payload: { taskId: ai_task.id } })`。`sendEvent` 失败不影响返回 200——Workflow 会在 `check-callback` / 超时后的 `recheck-callback` 中读到结果。

### 前端
- 提交后立即返回 `taskId`；任务列表 / 详情页使用上表参数轮询 `GET /api/ai/tasks/:id`，进入终态停止。
- 后续可升级为 Durable Objects + WebSocket 实时推送。

### 并发与防滥用
- 并发数检查与创建任务、预扣必须在**同一事务**中，并先取空间级事务锁，否则两个同时到达的请求都能通过 count 检查：
  ```sql
  BEGIN;
  SELECT pg_advisory_xact_lock(hashtextextended('ws:' || $ws, 0));   -- 同一空间的提交串行化，事务结束自动释放
  SELECT count(*) FROM ai_task WHERE ws = $ws AND status IN ('queued','running');   -- 须 < maxConcurrentTasks
  INSERT INTO ai_task (...);   -- 含 pricing 快照、provider_request_key、deadline_at
  -- hold()：锁批次并预扣（同一事务）
  COMMIT;
  -- 事务提交后再启动 Workflow；启动失败则将任务标记 failed 并 release
  ```
  Advisory lock 是事务级的，经 Hyperdrive 已实测可用：后到者等待先到者结束，提交、回滚或 Worker 中途结束后锁均释放（Phase 0 任务 7.1，见 `docs/07-infrastructure.md` §2「事务与锁」）。
- `RL_AI` 限流绑定按 workspace + user 限制提交频率，用于防刷和削峰。
- 限流绑定按数据中心分别计数、不精确，**不能用来实现配额**：需要精确保证的限制（并发任务数、积分余额、每日额度等）一律在 Postgres 事务里检查。
- 可选内容审核：提交前对 prompt 做审核（服务商自带或单独调用）。

`copyOutputsToR2` 只允许从该 provider 的已知域名下载（防 SSRF），限制最大文件大小与 MIME 类型。

## 5. 文件与输入素材

- 图生图 / 图生视频的输入，直传 R2 分三步：
  1. `POST /api/files/uploads`（声明 `mime`、`size`）：服务端校验 MIME 白名单、单文件上限、`已用 + size ≤ storageGb`，插入 `file(status='pending')`，返回预签名 PUT URL（有效期 10 分钟，签名包含 `Content-Type`）。
  2. 前端直传 R2。
  3. `POST /api/files/:id/complete`：服务端 `R2.head()` 取对象**真实**大小与类型，与声明不符或超出配额 → 删除对象、标记失败；通过则置 `status='ready'`。
  - 原因：R2 的预签名 PUT 无法限制上传体积（S3 的 POST policy `content-length-range` 在 R2 不可用），只能上传后校验。提交任务时只接受 `status='ready'` 的 `fileId`；Cron 清理超过 1 小时仍为 `pending` 的记录及对象。
  - 服务端给 provider 生成短期可读 URL。
- 产出文件访问：通过 `/api/files/:id` 鉴权后 302 到短期签名 URL；公开分享作为可选功能（`file.public_token`）。
- 预签名 URL 需要 R2 的 S3 兼容 API 凭证（`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`，令牌权限限定到 `FILES` 桶），用 `aws4fetch` 在 Worker 内签名。
- 配额：按 `sum(file.size) where status='ready' and deleted_at is null` 对照权益 `storageGb`。
