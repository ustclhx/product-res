# 06 · AI：文本、图片、视频

## 1. 总体设计

| 类型 | 执行方式 | 可选计费方式（按模型配置，见 §2） | 状态存储 |
|---|---|---|---|
| 文本 | 请求内流式（`streamText`），可带工具调用 | 按对话轮次 / 按 token | `ai_conversation` / `ai_message` |
| 图片 | 后台任务（Workflow；服务商可异步或同步产出） | 按生成次数 / 按张数（可按分辨率、步数加权） | `ai_task` + `file` |
| 视频 | 异步任务（Workflow + 服务商回调） | 按生成次数 / 按秒数（可按分辨率加权） | `ai_task` + `file` |

统一原则：
1. **先检查、再预扣、后调用**：权益（模型是否可用、并发数）→ 限流 → `credits.hold()` → 调用模型。
2. **产出落 R2**：服务商返回的 URL 会过期，结果一律转存 R2 并写 `file` 表。
3. **失败按类型结算**：文本最终失败且无可见正文时，每个工作区每滚动 1 小时的前 3 次全额释放，超出后按最后一次上游尝试的用量结算（见 §3「免费失败次数」）；有正文时按已产生用量计费，可通过模板配置改为所有失败全退；媒体失败释放预扣。未结算的 hold 由 Cron 兜底（见 05-billing「超时回收」）。
4. **文本出口由部署管理员选择**：Cloudflare 默认 AI Gateway/BYOK；Node 默认 OpenAI 兼容直连，可显式选择 Gateway。两出口使用同一预算与结算规则。

## 2. 模型注册表

`ai_model` 表（后台可编辑，KV 缓存）决定：模型对哪些套餐可见、走哪个 provider、如何计价、接受哪些参数。

### 计费方式

积分消耗支持三种计费方式，**按模型**在 `ai_model.pricing` 中选择——同一个站点可以让聊天按 token、视频按次，具体由站点的产品形态决定：

| 方式 | 适用 | 示例 | 预扣 | 结算 |
|---|---|---|---|---|
| `per_call` 按次 | 对话轮次、生成次数；价格对用户最直观 | 一轮对话 1 分；生成一个视频 5 分，1080p ×2 | 固定值 | 等于预扣，**不会超出** |
| `token` 按 token | 文本，成本随上下文和输出长度变化大 | 输入 2 分/1k，输出 8 分/1k | 估算上限 | 按实际 usage |
| `per_unit` 按用量单位 | 图片张数、视频秒数 | 每张 10 分；每秒 20 分 | 按请求参数计算 | 按服务商回报的 usage |

```ts
type Multipliers = Record<string, Record<string, number>>   // 参数名 → 取值 → 倍率，如 { resolution: { '720p': 1, '1080p': 2 } }

type Pricing =
  | {
      mode: 'per_call'
      credits: number                      // 每轮对话 / 每次生成的积分
      multipliers?: Multipliers            // 按请求参数加权，多个参数相乘
      chargeOn?: 'success' | 'any_output'  // 何时计费：媒体默认 success；文本默认 any_output（中断但已有输出也计费）
      limits?: { maxInputTokens?: number; maxOutputTokens?: number }  // 文本按轮计费时限制单轮成本上限
    }
  | { mode: 'token'; inputPer1k: number; outputPer1k: number; minCharge?: number }
  | { mode: 'per_unit'; unit: 'image' | 'second'; perUnit: number; multipliers?: Multipliers }

function estimateCredits(pricing, input): number   // 预扣用：per_call 为固定值，其余取上限
function actualCredits(pricing, usage): number     // 结算用：per_call 直接返回预扣值
```

- **按次计费的成本控制**：文本按轮计费时，平台的实际成本仍随上下文长度增长，必须配 `limits`（截断历史到 `maxInputTokens`、限制 `maxOutputTokens`），否则长会话会让单轮成本无上限。
- **默认值**：新建模型时的默认计费方式取 `template.config.ts` 的 `ai.defaultPricingMode`（如文本 `token`、图片和视频 `per_call`），后台可以逐个模型修改。
- **展示**：模型选择器与生成按钮旁显示本次预计消耗（按次直接显示固定值；按 token 显示「约 X–Y 分」）；用量页每条流水注明计费方式。

**定价快照**：`ai_model` 经 KV 缓存，后台改价后各地生效有延迟。为保证同一次调用的预扣与结算口径一致，发起调用时把当时的 `pricing` 写入 `ai_message.pricing` / `ai_task.pricing`，`estimateCredits` 与 `actualCredits` 都只读这份快照，不再重新读取 `ai_model`。改价只影响之后发起的调用。

`params_schema`（JSON Schema）用于：前端动态渲染参数表单、服务端校验输入，二者一致。

### 后台配置参数 schema

后台模型的新建、编辑和复制表单都提供 `params_schema` JSON 编辑框；必须输入 JSON 对象。文本模型可以填 `{}` 使用默认值，或配置 `x-text`。后台保存前使用共享的严格 schema 校验，拒绝未知键与非法值；已有非法文本配置在调用时整体降级为默认值。

| `params_schema['x-text']` 字段 | 类型 / 默认值 | 说明 |
|---|---|---|
| `tokensPerChar` | 正数 / `1` | 保守 token 估算系数 |
| `maxOutputTokens` | 正整数 / `4096` | 单次上游调用的输出上限 |
| `thinking` | 可选 boolean / 跟随 Provider adapter | 缺省由 adapter 决定是否可控；`false` 表示该模型禁用思考：不允许用户切换，adapter 可控时始终显式下发关闭形式（如 DeepSeek `thinking.type=disabled`）；`true` 表示支持，但无 adapter 时仍忽略模板与请求的开关 |
| `continuation` | `native` 或 `none` / `none` | 是否允许 Provider 原生前缀续写；还须 Provider 实现该能力 |

媒体模型使用提交页和服务端共用的 `parseMediaSchema` 校验，只支持平面 `string`、`number`、`integer`、`boolean` 字段，以及枚举、范围、长度等现有约束；不支持嵌套对象。建议先通过「Insert reference template」填入 JSON，再按具体模型调整。模板覆盖当前编辑框内容，保存前应核对服务商和 `providerModelId`：

| 参考模板 | 服务商 / 适用 `providerModelId` | 参数 |
|---|---|---|
| Text · x-text defaults | 所有文本模型 | `tokensPerChar=1`、`maxOutputTokens=4096`、thinking 缺省（跟随 Provider adapter）、`continuation=none` |
| Workers AI · FLUX schnell | `workers-ai` / `@cf/black-forest-labs/flux-1-schnell` | `prompt` 长度 1–2048，`steps` 默认 4、上限 8；模板要求至少 1 步 |
| fal · FLUX schnell | `fal` / `fal-ai/flux/schnell` | `prompt`、`image_size` 六种尺寸枚举（默认 `landscape_4_3`） |
| fal · Wan v2.2 turbo | `fal` / `fal-ai/wan/v2.2-a14b/text-to-video/turbo` | `prompt`、`resolution`（`480p` / `580p` / `720p`，默认 `720p`）、`enable_prompt_expansion=false` |

参数名与取值以 [Workers AI FLUX schnell](https://developers.cloudflare.com/workers-ai/models/flux-1-schnell/) 和 [fal FLUX schnell](https://fal.ai/models/fal-ai/flux/schnell/api) 的官方文档为依据。fal 的自定义 `image_size` 对象不属于当前平面表单支持范围，参考模板使用官方枚举。模板是指定模型的起点，不能直接套用于同一服务商的任意模型。

Wan 模板遵循 [Wan v2.2 turbo 官方输入](https://fal.ai/models/fal-ai/wan/v2.2-a14b/text-to-video/turbo/api)，支持 [PR #93 录制请求](../packages/ai/src/media/fixtures/fal.recorded.json) 使用的 `prompt`、`resolution=480p`、`enable_prompt_expansion=false`；模板的分辨率默认值采用官方的 `720p`。该端点不支持 `duration`，模板不提供时长参数；此模板应配按次计费，不能把未提供的时长当作按秒计费依据。

保存后的 schema 用于未来提交的参数表单、校验和预算；已提交任务继续使用提交时校验后的参数与定价快照。创建和编辑的审计仅记录 `params_schema` 的哈希摘要（编辑含前后哈希），不保存完整 schema JSON。

## 3. 文本

### staging 故障模型的配置与权限

`AI_FAULT_INJECTION=enabled` 只允许显式 `SENTRY_ENVIRONMENT=staging`，由 web/jobs
的 Cloudflare 与 Node 环境装配校验。开关仅写在两个 Wrangler 文件的 staging vars；
缺失或 `disabled` 时正常模型保持原行为。production 配置任何该开关值（包括 `disabled`）、
未知环境开启或非法值均拒绝，错误仅报告变量名。

故障模型 key 必须以 `acceptance-fault-` 开头，并在 `params_schema` 顶层声明
`"x-acceptance-fault": { "mode": "fal-callback-lost" }`。媒体仍需完整的平面 schema；
扩展不会进入表单字段或 Provider 业务参数。合法模式限 Workers 的 `workers-error` /
`workers-timeout`（`workers-ai`、图片、`@cf/black-forest-labs/flux-1-schnell`），fal 的
`fal-callback-lost` / `fal-callback-early` / `fal-submit-response-lost` /
`fal-provider-error` / `fal-timeout`（图片、`fal-ai/flux/schnell`），以及文本的
`chat-before-stream` / `chat-mid-stream`（`deepseek`、`deepseek-flash`）。
前缀和元数据必须同时成立；不匹配或缺失时不能降级成普通模型。

故障列表与调用要求实时、未模拟的平台管理员会话；空间 owner/admin 与所有 API key 均无权限。
KV 保存完整注册表，每次读取后按环境和身份过滤，提交直接读库再次核验，仍执行原套餐权益、
余额、并发和限流。后台保存、复制、启用共用配置校验；复制不能去除故障标识，且副本先停用。
关闭闸门后仍可停用遗留模型，故障模型不可见、不可选。媒体提交冻结已接受任务的模式，
runner 每个持久步骤重新核验闸门，关闭后走失败结算释放预扣，禁止切换成真实普通调用或继续查询/取消。
故障模型由独立套件经后台创建、最终停用，
不写迁移种子，调用请求不能携带模式或时间策略。

### thinking、reasoning 与自动恢复

产品形态在 `template.config.ts` 配置，不由运行时设置覆盖：

| 配置项 | 默认值 | 行为 |
|---|---|---|
| `ai.text.enabled` | `true` | 是否启用文本对话 |
| `ai.text.thinking.default` | `'off'` | adapter 可控时默认显式下发关闭思考；可改为 `'on'` 显式开启。模型显式声明 `thinking=false` 时不论该项都下发关闭 |
| `ai.text.thinking.userToggle` | `false` | 启用且 adapter 可控、模型未显式声明 `thinking=false` 时显示并接受逐条开关；关闭时携带请求 thinking 字段返回 400，启用但模型不可控时忽略该字段 |
| `ai.text.reasoning.display` | `false` | 开启时独立保存最终 attempt 的 reasoning 并折叠展示；关闭时不保存、不下发 |
| `ai.text.failedReplyRefund` | `'no-visible-output'` | 无可见正文的 failed 在免费次数内全退；`'all'` 为所有 failed 全退（不计次数） |

运行时设置 `ai.freeFailures`（`packages/db/src/settings.ts`，后台「运行时设置」页可编辑，默认 `{ count: 3, windowSeconds: 3600 }`）控制无可见正文失败的免费次数与滚动窗口，见下方「免费失败次数」。

只有非空 `text-delta` 算可见正文，reasoning 不算正文。正文出现前，瞬时错误（限流、5xx、网络与超时）、空回复与仅 reasoning 回复在同一预扣下最多重试 2 次，退避 1 秒 / 3 秒；展示 reasoning 时重试清空前一次思考并提示“重试中”。已有正文后流中断，模型声明 `continuation: 'native'` 且 Provider 支持时最多续写 2 次，正文追加到同一条消息。每 attempt 使用 `maxRetries: 0`，用户主动停止不触发自动恢复，超过 hold 截止时间不再重试。

**上游超时**：每次 attempt 新建 `AbortController`，与用户停止信号经 `AbortSignal.any` 合并后交给 `streamText`。空闲超时 `UPSTREAM_IDLE_TIMEOUT_MS`（60 秒）在每收到一个上游片段时重置；总超时为本次回复的 hold 截止时间。任一超时触发时中止本次上游请求，并放弃等待未返回的读取（不依赖 Provider 响应中止信号），错误归为可重试的 `AI_UPSTREAM_TIMEOUT`：正文前按上面的规则重试，有正文后尝试续写，否则按失败结算。心跳只写给客户端，不重置上游空闲计时；结束时心跳与超时定时器一并清理。

当前仅 DeepSeek adapter 可控 thinking：统一 `reasoning` 参数配合 `providerOptions.deepseek.thinking.type=enabled|disabled`。模型 `params_schema` 为 `{}` 或未声明 `x-text.thinking` 时跟随 adapter，默认始终按模板或允许的请求值显式下发开/关；显式 `false` 时不允许用户切换，并**显式下发关闭**（`reasoning: 'none'` 与 `thinking.type=disabled`），而不是省略——DeepSeek V4 等模型默认推理，省略时 reasoning token 计入 `maxOutputTokens`，长输出会被截断（0.5.0 前为省略，xuanxue 实测发现）。显式 `true` 也不能为其他 Provider 增加控制能力，无 adapter 时忽略开关并保持原行为。后台 Text 参考模板不填写 thinking 字段，跟随 adapter；已有模型的显式 `thinking=false` 继续禁用用户切换，后台严格校验保持不变。

实际下发值由 `@product-res/ai` 的 `resolveTextThinking(provider, override, requested)` 统一计算：Provider 不可控 → `undefined`（不改请求）；
`override === false` → `false`；否则为 `requested`。`supportsTextThinking` 只决定是否向使用者开放开关（模型选择器）。使用它的入口：
站内对话与 `/v1/chat/completions`（同一 `startWorkspaceChat`），推荐问题（`requested=false`，Provider 可控时总是显式关闭，避免 256 token 上限被 reasoning 耗尽），
文本故障注入（固定关闭），提示词评测的评委（见下文）。各 Provider 的 `applyThinking(false)`：

| Provider | 关闭形式 | 说明 |
|---|---|---|
| `deepseek` | `reasoning: 'none'` + `providerOptions.deepseek.thinking.type='disabled'` | 唯一已登记 adapter |
| `anthropic` | 不下发 | 未开启 extended thinking 时本就不思考，省略即关闭 |
| `openai` | 不下发 | 非推理模型拒绝 reasoning 参数，推理模型多数不能完全关闭，无法按 Provider 统一 |
| `google` | 不下发 | Gemini 2.5 Flash 可用 `thinkingBudget: 0` 关闭，Pro 不能关闭，属于模型级差异 |
| 其他 / `workers-ai` | 不下发 | 无 adapter |

衍生项目需要为其他 Provider 控制思考时，在 `packages/ai/src/text/capabilities.ts` 登记 adapter，并为其 `applyThinking(false)` 加单测。

已安装的 `@ai-sdk/deepseek@3.0.63` 原生支持末条 assistant 的 `providerOptions.deepseek.prefix=true`，SDK 将其映射为请求消息的 `prefix: true`。模型工厂仅为这类续写请求选择 `/beta` base URL（直连 `https://api.deepseek.com/beta`，Gateway 为 `/deepseek/beta`），普通请求沿用原端点，无需自定义 fetch/body 转换。此结论由本地 SDK 与假 fetch 测试核验，不代表已完成真实 Provider / staging 验收。

reasoning 仅以独立 `{ type: 'reasoning', text }` part 存储，永不进入历史上下文。后续请求包含 completed / aborted / failed 消息中的可见正文，包括失败前已生成的部分回复；`messageText` 只拼接 text part。API key completions 始终过滤 reasoning，不返回 `reasoning_content`。

### 文本计费矩阵

下表中的失败指重试或续写耗尽后的最终 failed；所有尝试共用一份 hold 与一条 assistant 消息。

| 最终状态 | `failedReplyRefund` | `token` | `per_call` |
|---|---|---|---|
| completed | 任意 | 最终成功 attempt 的输入 + 产生可见正文的各 attempt 输出（含其 reasoning） | 固定费用一次 |
| failed，无正文（含仅 reasoning），免费次数内 | `'no-visible-output'` | 全额释放 | 全额释放 |
| failed，无正文，超出免费次数 | `'no-visible-output'` | 最后一次 attempt 的输入 + 输出（含 reasoning），不低于 `minCharge`，封顶 hold | 固定费用一次（与 `chargeOn` 无关），封顶 hold |
| failed，无正文 | `'all'` | 全额释放 | 全额释放 |
| failed，有正文 | `'no-visible-output'` | 按已产生用量，封顶 hold | 默认 `any_output` 收固定费用一次；`success` 则释放 |
| failed，有正文 | `'all'` | 全额释放 | 全额释放 |
| aborted，用户主动停止 | 任意 | 沿用已产生用量的估算，封顶 hold | 沿用 `chargeOn`：默认有正文收费，否则释放 |

`reasoningTokens` 单独记录，同时属于 `outputTokens`，不能再重复相加收费。检查点 JSON 的 `total` 记录所有 attempt 的累计输入、输出和 reasoning 用量；正文前被丢弃的 attempt 另记 `absorbed`，成本由 SaaS 承担，不计入用户扣费。检查点包含 reasoning 的估算 token；正文前重试时重置被丢弃 attempt 的检查点贡献。超时回收同样先判断持久化正文：没有正文时按免费失败次数处理，有正文时按最后检查点结算且封顶 hold；`failedReplyRefund='all'` 也适用于回收失败。

#### 免费失败次数

无可见正文的失败没有给用户产出，但上游已经计费，完全免费会被反复刷。结算这类失败时，`settleInterruptedChatMessage` 先取工作区积分咨询锁，在锁内统计该工作区窗口内 `role='assistant' and status='failed' and credits=0` 的 `ai_message` 行：时间下界用 UUIDv7 的毫秒前缀构造（`uuidv7Floor`），复用 `(workspace_id, id desc)` 索引，不新增表或计数器。计数小于 `ai.freeFailures.count` 时全额释放；否则按检查点中 `lastAttempt`（text-stream 每次 attempt 整体替换，只保留最后一次的输入、输出与 reasoning）结算。收费的失败 `credits > 0`，不占用免费次数；窗口滚动出最早的免费失败后恢复免费。并发失败在同一把锁内串行计数，不会同时读到旧值。超时回收器走同一函数：检查点没有 `lastAttempt` 时，按 token 收 `minCharge`，按次收固定费用，都不超过 hold。

### Gateway 与密钥

部署管理员通过 `AI_TEXT_EGRESS=direct|gateway` 选择出口，非法值校验失败。Cloudflare 缺省为
`gateway`，Node schema 缺省为 `direct`，Node composition 应原样注入这项配置。
模型后台只管理 provider、模型 ID、参数和定价，没有端点或密钥列；本轮无 schema 变更。

直连时，在部署 env 配置 `OPENAI_BASE_URL`（完整 HTTP(S) API base，如 `https://compatible.example/v1`）
和 `OPENAI_API_KEY`，Node 也可用 `OPENAI_API_KEY_FILE` 挂载 secret；直接值与 `_FILE` 不能同时提供。
后台文本模型 provider 填 `openai`，Provider model ID 填兼容服务接受的模型 ID。
URL 不接受内嵌用户名/密码、query 或 fragment；普通聊天请求不能指定端点。直连不要求 Gateway
配置、不发送 `cf-aig-*` 头，不读取 SDK 的隐式进程密钥；缺少管理员 key 时在预扣前返回 503。
`deepseek` 例外：Cloudflare AI Gateway 会把 DeepSeek 的 SSE 整段缓冲到生成结束才返回
（2026-10-13 实测 `/deepseek` 与 `/compat` 端点、BYOK 或显式密钥、跳过缓存与日志均如此，
同一 Gateway 的 Workers AI 正常逐块；见 issue #152），用户只能看到一次性到达的回复。
因此 `AI_TEXT_EGRESS=direct` 且配置了 `DEEPSEEK_API_KEY` 时，DeepSeek 直连官方
`https://api.deepseek.com`，不发送 `cf-aig-*` 头；未配置该密钥时仍走下面的 Gateway（BYOK）路径。
需要逐步显示回复的 Cloudflare 部署应设置 `AI_TEXT_EGRESS=direct` var 与 `DEEPSEEK_API_KEY` secret
（此时 `openai` 模型也按上文要求 `OPENAI_BASE_URL`）。
其他原生 provider 保持下面的 Gateway 路径，`AI_TEXT_EGRESS` 不为它们新增直连协议。

文本调用有两种密钥存放方式，均经 `https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}` 转发：

- **默认 BYOK**：在 Cloudflare AI Gateway 的 **Provider Keys** 为所用服务商保存 API Key（使用 `default` alias），开启 Gateway 鉴权。Worker 只需 `AI_GATEWAY_TOKEN` secret 与 `AI_GATEWAY_ACCOUNT_ID` / `AI_GATEWAY_ID` vars；请求不发送 Provider 授权头，由 Gateway 注入所存密钥。SDK 所需的占位 API Key 不能出现在最终请求的 Provider 授权头中，否则 Gateway 会转发占位值而不会使用 BYOK。见 [Cloudflare BYOK](https://developers.cloudflare.com/ai-gateway/configuration/bring-your-own-keys/)。
- **可选 Worker secrets**：把所用 Provider 的 API Key 存为 Worker secret，本地写入 app `.dev.vars`；模型工厂按服务商发送对应授权头，经 Gateway 转发给 Provider。支持 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`、`GOOGLE_API_KEY`、`DEEPSEEK_API_KEY`；显式提供的 Provider 密钥优先于 Gateway 中的 BYOK。

`AI_GATEWAY_TOKEN` 用于 Gateway 鉴权，请求头为 `cf-aig-authorization: Bearer <AI_GATEWAY_TOKEN>`，与 Provider 授权分开；token 需有 Cloudflare **AI Gateway Run** 权限。见 [Authenticated Gateway](https://developers.cloudflare.com/ai-gateway/configuration/authentication/)。Provider 路径与可选密钥映射如下：

| Provider | Gateway 路径（接在上述前缀后） | 可选 Worker secret | Provider 授权头 |
|---|---|---|---|
| [OpenAI](https://developers.cloudflare.com/ai-gateway/usage/providers/openai/) | `/openai` | `OPENAI_API_KEY` | `Authorization: Bearer <key>` |
| [Anthropic](https://developers.cloudflare.com/ai-gateway/usage/providers/anthropic/) | `/anthropic`（消息接口 `/v1/messages`） | `ANTHROPIC_API_KEY` | `x-api-key: <key>` |
| [Google AI Studio](https://developers.cloudflare.com/ai-gateway/usage/providers/google-ai-studio/) | `/google-ai-studio`（SDK 使用 `/v1beta`） | `GOOGLE_API_KEY` | `x-goog-api-key: <key>` |
| [DeepSeek](https://developers.cloudflare.com/ai-gateway/usage/providers/deepseek/) | `/deepseek` | `DEEPSEEK_API_KEY` | `Authorization: Bearer <key>` |

本地注入与线上 secret 配置见 [基础设施 §4](./07-infrastructure.md#4-环境变量与绑定清单)。根 `.env.local` 的默认 dev 支付同步不加载 AI 密钥。2026-10-12 已用默认模型工厂与 AI SDK 的 `generateText`、`streamText` 对 DeepSeek `deepseek-flash` 分别完成本地真实调用：仅传 Gateway 配置，使用托管密钥（BYOK），未传 `DEEPSEEK_API_KEY`，均回复 `OK.`，usage 为输入 7 / 输出 2 tokens。中断流日志回查仍因缺少 AI Gateway 日志读取权限的 token 阻塞，详见 change design 的 Open Questions；这次验证不替代 staging 计费验收。

### 流程

staging 文本故障在正常模型工厂产生的 `doStream` 外包装，不在预扣前的构造阶段抛错。
模式在 fresh 管理员 gate 后冻结；assistant 初始检查点保留预算输入估算、0 输出及
`acceptanceFaultProof`（版本、mode、phase、injected、realProviderCalled、upstreamCalls）。
正常 token 检查点与证明使用局部 JSON 合并，结算保留证明；实际进入注入分支且证明写入成功后，
才能记 `injected=true`。上游自然错误、输出未达到阈值或证明写入失败不能认证故障注入成功。

| 模式 × 定价 | 上游与输出 | 结算预期（默认失败退款口径） |
|---|---|---|
| `chat-before-stream` × `per_call` | 不调用上游，无 assistant 输出 | failed、全额释放、0 消费 |
| `chat-before-stream` × `token` | 不调用上游，无输出；保留预算输入估算 | failed、全额释放、0 消费 |
| `chat-mid-stream` × `per_call` | 调用上游一次，转发到至少200估算输出 token 后流异常 | 保留真实部分回复，failed、固定费用消费一次 |
| `chat-mid-stream` × `token` | 同上，用原模型 tokensPerChar 估算 | failed、按已产生用量/minCharge 精确计算并封顶 hold，无额外补扣、欠费或超额承担 |

所有文本 attempt 均设置 `maxRetries=0`，故障调用的输出上限最多1024。流中注入取消上游 reader，通过
`controller.error` 结束，不能只发送 error chunk 再 close，也不触发业务“用户停止”控制器；
异常不会被 onEnd 认证成 completed。独立本地假上游仍经过该包装器；未知 Provider/model ID
明确拒绝，不回退真实服务商。流前证明是合成错误，流中才包含上游实际调用及部分文本的业务证据；
本地夹具不作为真实 staging 或 Gateway token 差异证据。

```
1. 解析会话、校验模型可用；取定价快照 pricing
2. 计算预扣额与 maxOut：
   per_call：amount = credits × multipliers；按 limits 截断历史，maxOut = limits.maxOutputTokens ?? 模型上限
   token：   inputCost = inputTokens(字符估算) * inputPer1k / 1000
             maxOut = min(模型/请求的 maxOutputTokens, floor((balance - inputCost) * 1000 / outputPer1k))
             outputPer1k=0 时不按余额收缩输出，仍校验输入费用与最低费用
             若 maxOut < minOutputTokens（默认 256）或余额不够 minCharge → INSUFFICIENT_CREDITS
             amount = max(ceil(inputCost + maxOut * outputPer1k / 1000), minCharge ?? 1)
3. hold(amount)                                     // expires_at = now + 10min
   插入 assistant message（status='streaming', hold_id）
4. 在同一 hold 下编排 streamText attempts（maxRetries: 0），按上述规则重试或续写
5. ctx.waitUntil(done)                              // done 包含 consumeStream、等待检查点写入、结算
   onChunk 收到新正文或 reasoning 时：每 5 秒或新增 200 个估算输出 token 写 usage_checkpoint 与已生成内容
6. 保存合并正文与 usage；开启展示时保存最终 attempt 的 reasoning；读流及检查点写入完成后：
   正常结束 → 按上述矩阵结算；缺失 usage 时按封顶估算结算 → completed
   最终失败 → failedReplyRefund='all' 或无正文且未超出免费次数：release；
              无正文且超出免费次数：按最后一次 attempt 用量；否则按部分用量结算 → failed
   用户停止 → 沿用按已产生用量 / chargeOn 的规则，金额不超过 hold.amount → aborted
```

- **按余额压低 `maxOutputTokens`**（仅 token 计费）：按模型上限全额预扣，会让余额不多的用户连短对话都发不出去；改为按余额计算本次可用的最大输出，余额只够很短的回复时才拒绝。
- **输入 token 估算**：`packages/ai/src/text/budget.ts` 按 Unicode 码点计数，每条消息为 `8 + ceil(字符数 × tokensPerChar)`，所有消息相加；默认系数 `tokensPerChar=1`。模型可在 `ai_model.params_schema['x-text']` 配置正数系数与 `maxOutputTokens`（默认 4096），缺失或配置不合法时使用默认值；首版没有调用服务商计数接口。按次文本模型从最早的历史开始丢弃，直到估算输入符合 `limits.maxInputTokens`；最后一条消息仍超限时返回 `INPUT_TOO_LONG`。估算用于预算与中断兜底，不是服务商的精确分词结果；输入低估可能导致真实 usage 费用超过预扣，按 05-billing「超额容忍」处理。正常完成优先使用 AI SDK 的最终输入 / 输出 usage，缺失的字段分别回退为输入估算 / 最终文本估算；只要使用了估算，结算金额就不超过预扣额。
- **客户端中断后的结算**（平台行为见下方 Phase 0「实测记录」）：第 5 步把服务端读流、等待检查点写入和结算一起放入 `waitUntil`；用户关闭页面后服务端仍继续读流。模型在**断开后 30 秒内**输出完毕时，`onEnd` 保存最终 usage，随后结算并保存完整回复（被中断的回复仍按完整输出计费）。客户端保持连接时不受这个断开后的 30 秒时限约束。显式停止使用 `POST /api/ai/chat/:messageId/stop`：同一 isolate 中 abort 上游，按内存中的已生成文本估算结算；其他 isolate 按已持久化的最后一个检查点结算，原读取器在下次写检查点时发现消息已结束后 abort。停止回复标记为 `aborted`。
- **收到 start 之前停止**（issue #362）：回复 ID 只在流的 `start` 事件中下发，客户端在此之前（`submitted`）点停止时，改用 `POST /api/ai/chat/stop`，请求体 `{ slug, conversationId, requestId }`。`requestId` 是站内客户端每次发送时生成、随 `POST /api/ai/chat` 提交的 UUID，服务端写入回复的 `usage_checkpoint.clientRequestId`（检查点 JSON 各写入以 `||` 合并保留，无需迁移）。停止接口只认本人在该空间的对话（否则 404），并按 (对话, 请求 ID) 查回复：
  - 先在本 isolate 登记「停止已请求」标记（键为用户 ID + 请求 ID，60 秒过期）。原请求在本 isolate 时，建好消息后、调用模型前检查标记，命中即不调用上游，以零输出按停止规则结算（按次释放预扣，按 token 收 `minCharge`），与生成前点停止的结果一致。
  - 查不到回复时按 0 / 100 / 200 / 400 / 800 / 1600 / 3200 毫秒间隔重读（约 6 秒，覆盖原请求在其他 isolate、尚未入库的情况）。找到后与按回复 ID 停止完全相同：本 isolate abort 并按内存结算，其他 isolate 按检查点结算、原读取器在下次写检查点时 abort（与跨 isolate 停止相同，上游可能多生成一段，但不计费）。返回 `{ status, messageId }`。
  - 等待期内仍没有回复（请求被拒或入库前处理异常缓慢）时返回 `{ status: 'aborted', messageId: null }`。原请求若落在其他 isolate 且在等待期之后才入库，仍会完整生成并结算，这是不引入共享存储时保留的边界。
  - 拿到回复 ID 后客户端仍走 `/api/ai/chat/:messageId/stop`，原有行为不变；省略 `requestId` 的旧客户端与公开 API 不受影响。
- **空闲心跳**：Cloudflare 代理（橙云）与 Tunnel 后的源站在开始响应前或两段数据之间约 100 秒无字节即被边缘返回 524（Free/Pro/Business 不可调）；Nginx 等反向代理的默认读超时更短（如 `proxy_read_timeout` 60 秒）。推理模型在 reasoning 不展示时可能长时间不输出，因此 `createChatStream` 在任何片段（正文、展示的 reasoning、重试信号）之后静默满 `STREAM_HEARTBEAT_MS`（25 秒）即补发心跳，真实输出重置计时，流结束、失败或消费方取消时清理定时器。站内对话流写成 `{"type":"data-keepalive","data":null,"transient":true}`，transient 数据片段不进入 `useChat` 的消息 parts；OpenAI 兼容流写 SSE 注释行 `: keepalive`，按 SSE 规范客户端忽略。两条流都在等待首个 token 前写出 `start` / role 首片段，响应头随之发出。心跳不影响检查点、预扣与结算；Workers 直接响应不受源站 100 秒限制，心跳在该形态下同样无害。
- **兜底**：Phase 0 实测 `waitUntil` 的时限是**客户端断开（或响应结束）后 30 秒**。超时后运行时直接取消剩余任务（日志：`waitUntil() tasks did not complete within the allowed time after invocation end and have been cancelled`），结束回调、`catch` / `finally` 不会执行，回复可能丢失结算。对话 hold 的有效期为 10 分钟，过期后由 Jobs 的 `ai_message` 回收处理器结算。
  - **用量检查点**：`onChunk` 收到新文本或 reasoning 时判断距上次检查点是否已过 5 秒，或新增估算输出是否达到 200 token，先到者触发；没有新输出时不写入。写入串行、不阻塞读流，把 `{inputTokens, outputTokens, reasoningTokens, absorbed, total, lastAttempt, at}` 与截至检查点的正文一起保存（仅开启展示时另存 reasoning part），只更新 `streaming` 消息；写入失败只记日志。输入沿用发起时的估算，输出包括正文与 reasoning 的估算，reasoning 另记 `reasoningTokens`。检查点只保存了部分文本，估算 token 数可能高于服务商实际分词数（英文尤其明显），按检查点结算以预扣额封顶；封顶不等于精确用量，仍需通过最终 usage 与估算的差异校准模型系数。正常完成时检查点不参与结算金额。
  - **最低费用（Q7）**：结算丢失时，回收按 failed 口径：开启所有失败全退时全额释放；无持久化正文（即使检查点已有 reasoning 输出）时按「免费失败次数」处理，次数内全额释放。有正文时，按 token 使用最后一个检查点的输入 / 输出用量，金额为 `min(max(ceil((inputTokens × inputPer1k + outputTokens × outputPer1k) / 1000), minCharge ?? 1), hold.amount)`；按次默认 `any_output` 收取固定费用，`success` 则释放。回收处理器把消息标为 `failed`，保留截至最后检查点的部分回复；结算和消息更新在同一事务内，通过 hold 状态避免重复结算。
  - 未采纳：断开约 25 秒后主动中止生成——会截断用户的回复，且中止后服务商不一定返回 usage。代价是断开超过 30 秒后服务商仍在生成的那部分输出平台无法收费，作为已接受的取舍，通过监控被取消的回复数量评估；影响明显时再考虑主动中止，或由 Durable Object 承载超长生成。
  - 观测注意：客户端断开的请求在 Workers Logs / `wrangler tail` 中的 `outcome` 为 `canceled`，即使 `waitUntil` 中的结算已成功完成；判断是否结算要看 `ai_message.status`，不能看请求的 `outcome`。

- **估算结算封顶（tasks 2.8）**：停止（同一 isolate 的内存估算或跨 isolate 的检查点）、出错和超时兜底都以 `min(估算金额, hold.amount)` 结算；`minCharge` 下限先应用，再受预扣额封顶。这些路径不触发超额容忍、不补扣余额、不产生欠费。结算入口显式区分真实 usage 与估算，为 tasks 2.9 取回实际用量保留入口；当前尚未实现 AI Gateway 用量回查。
- 服务商报告的真实 usage 费用超过预扣时，**不中断生成**，输出完成后按 05-billing「超额容忍」结算：额度内由平台承担，超出额度的部分从余额补扣，余额不足记为欠费。
- 上下文管理：按模型 context window 截断历史；长会话可做摘要（后续）。
- 工具调用、RAG：作为扩展点（`tools` 注册表），模板首版只提供示例工具。

### 对象对话、推荐追问与评分（add-subject-chat）

- **绑定对象**：`ai_conversation.subject_type` / `subject_id` 记录对话来源（`subject_id` 是不透明 ID，不放个人信息）。
  项目在 `apps/web/src/features/ai/subject-providers.ts` 调用 `registerConversationSubject(type, provider)` 注册类型：
  `label(locale)` 给对话列表显示来源标签；`resolve(ctx, id)` 必须同时校验 `ctx.workspaceId` 与 `ctx.userId`，
  查不到返回 null（与未注册类型一样统一 404），返回标题、默认模型 key、按语言的开场推荐问题与 `context()`。
- **上下文只写一次**：新建对象对话时服务端调用 `context()`（`{ version, text?, data? }`），写成首条 system 消息，
  以 `[context type=<type> version=<version>]` 开头。之后每轮 `POST /api/ai/chat` 把它作为固定前缀放在最前
  （Anthropic 带 `cacheControl`），按输入上限截断时保留。客户端只能传对象引用或令牌，聊天请求体仍是 strictObject。
- **嵌入**：在任意 App 页面放 `<SubjectChat slug subjectType subjectId />`（`features/ai/subject-chat.tsx`），默认进入最近一个对话。
  外壳为 `@product-res/ui` 的 `EmbeddedChat`：`variant` 默认 `inline`（≥ 768px 为正文卡片），`panel` 为悬浮按钮 + 右侧面板，手机上都是底部抽屉；
  关闭外壳不停止生成，再打开时消息与草稿仍在（add-ai-chat-components）。工具卡片的显示名在项目自有的 `message-parts.project.tsx` 登记。
  模型列表来自用户生效套餐的 `features.models`（与对话页相同），列表为空时不能开始对话，模板文案为「No models are available on your current plan」。
  排查时先区分两种情况：模型已在 `/admin/models` 启用但套餐未授权（新项目首次 seed 的 `free.features.models=[]`，见 [创建项目](./create-project.md)），
  在 `/admin/billing/plans` 为相应套餐多选模型 key 并保存，下一次请求生效；还是模型本身未创建或未启用，先到 `/admin/models` 处理。
  项目改写这句文案时保留「当前套餐」的含义，避免与模型服务故障混淆。
- **临时上下文**：没有持久对象时，服务端用 `issueSubjectContext({ secret, cache }, { userId, workspaceId, subjectType, context, title?, suggestions?, returnTo })`
  把上下文存进 KV（随机键，30 分钟）并签发令牌，跳转 `/app/<slug>/chat/context?token=<token>`。
  令牌只签名不加密、不含正文，绑定用户与空间；上下文总长度不超过 20 万字符；篡改或他人令牌显示无效，过期显示返回原页（`returnTo` 只接受站内路径）。
  类型也需注册（可只给 `label`）。上下文必须由服务端复算或读取，不能直接使用客户端提交的内容。
- **后续推荐问题**：`template.config.ts` 的 `ai.text.followUps`（默认 `{ enabled: false, charge: false, count: 3, modelKey: null }`）。
  开启后每条完成的回复最多调用一次模型（结果缓存在 KV 1 天）。`charge: false` 时由平台承担；`charge: true` 时预扣挂在被追问的回复上、
  按实际 token 用量结算、生成失败释放，同一回复已有在途预扣时不再生成；计费模式只对按 token 计价的模型生成（按次计价会每次收一轮完整费用，直接跳过）。
  建议用 `modelKey` 指定一个便宜的按 token 计价模型。推荐问题不写入历史。
- **评分**：每用户每条回复一条（`ai_message_feedback`），可修改、可撤销，文字反馈入库前去除疑似密钥；
  后台 `/admin/feedback` 查看列表与按模型、对象类型的满意率，可删除单条（审计不含反馈文字）。删号与删空间清理先删评分再删消息。
  点踩表单可勾选「共享这条回复及之前几条消息，用于改进回答」（默认不勾选，每条反馈单独同意，再次提交时不勾选、改为点赞或撤销即撤回）；
  只有同意的反馈后台才能查看被评回复与它之前最近 3 条消息（不含对象上下文），服务端检查同意并为每次查看写审计。
  项目上线前应在隐私政策中说明这项共享。
- 日志只记录对象类型与上下文版本（`ai.subject_conversation.created`），不记录上下文正文。

### 提示词版本与评测（add-prompt-evals）

改一次提示词，要能看出哪些样本变好、哪些变差，并能离线重复同一次对比。模板提供两部分：
`@product-res/ai` 的提示词定义（业务无关、可在 Worker 中使用），以及只供命令行使用的评测工具
`packages/evals`（`pnpm eval:prompts`）。任何应用或运行时包都不得依赖 `@product-res/evals`（`pnpm check:deps` 检查）。

**定义提示词**：生产代码与评测套件导入同一个定义，评测测的就是线上用的提示词。

```ts
import { definePrompt, renderPrompt } from '@product-res/ai'

export const reportV4 = definePrompt<ReportInput>({
  id: 'report', // 小写字母、数字、短横线
  version: 'v4', // 同一 id 下唯一
  system: '…', // 字符串或 (input) => string
  user: (input) => `…`,
  sections: [{ id: 'summary', heading: '总结' }], // 期望章节，供检查与评委使用
  maxOutputTokens: 4000,
  params: { temperature: 0.4 },
})
// reportV4.promptVersion === 'report@v4'
const { system, user, params, maxOutputTokens } = renderPrompt(reportV4, input)
```

- 定义模块保持纯函数：不导入数据库、`@/` 等 app 别名或运行时绑定，命令行才能直接加载；
  只用 Node 类型剥离支持的 TS 语法（不用 `enum`、`namespace`、参数属性），相对导入带 `.ts` 扩展名。
- **版本不可变**：已用于生成或评测的版本，内容一改就新建版本（`v4` → `v5`），旧版本保留在套件中作基线。
- **生成记录保存版本**：项目自有的生成表加列 `prompt_version text not null`，写入 `promptVersion`（如 `report@v4`），
  结构化日志同时记录 `promptVersion` 字段，以便把线上结果与评测报告中的同一版本对应。模板的 `ai_message` 不加此列。

**套件目录**：项目套件放在根目录 `evals/<suite>/`（项目自有，模板不在此交付文件，`template-sync` 不会覆盖）；
模板示例在 `packages/evals/example/`（`--suite example`）。

```
evals/<suite>/
  suite.ts             # export default defineSuite({...})，从 @product-res/evals 导入 defineSuite 与 checks
  samples.json         # 固定样本：[{ id, input, expect?, tags? }]
  prompts.lock.json    # 版本锁，运行时自动追加，随套件提交
  recordings/<promptVersion>/<modelKey>/<sampleId>.json               # 生成录制
  recordings/<promptVersion>/<modelKey>/<sampleId>.judge.<judgeKey>.json  # 评委录制
  README.md            # 可选：录制日期、模型与费用
```

- `defineSuite({ name, prompts, defaultPrompt?, models, generator, judge?, checks?, regressionThreshold?, prepareOutput?, evaluateRun? })`
  （后两个扩展点见下文「被评正文转换与评测后门槛」）；
  `models` 的每项为 `{ provider, providerModelId, priceUsd: { inputPerMTok, outputPerMTok }, tokensPerChar?, thinking? }`，
  单价单位是**美元 / 百万 token**（不读后台模型表，后台单价是积分）。
  模型可选 `thinking?: boolean`，**与线上模型行的 `x-text.thinking` 同样声明，评测才与线上一致**：缺省不改请求（Provider 默认）；
  `true` / `false` 在生成调用中经 `resolveTextThinking` + `applyThinking` 下发（Provider 可控时为开启 / 关闭，不可控时忽略）。
  该字段只作用于生成，评委用 `judge.thinking`。它不进入渲染摘要与版本锁，录制也不按它判过期：改了生成模型的 `thinking` 后需重新录制。
- 样本 `input` 原样传给 `user(input)`；`expect` 按检查 ID 覆盖或追加套件级参数，`expect.<检查>.severity: 'warn'`
  可把该检查对这个样本降为警告。样本必须是**合成或已脱敏**的数据：录制含模型输出，会随仓库提交。
- **版本锁**：每次运行（含回放）都重新渲染每个版本 × 每个样本，比对 `prompts.lock.json` 中的输入摘要与渲染摘要。
  「`report@v3` content changed … create a new prompt version」表示该版本的渲染结果变了，应新建版本；
  「sample … input changed … add a new sample id」表示样本被改了，应新增样本 ID 而不是修改旧样本。两种都以退出码 2 失败，锁保持原值。
  渲染摘要包含 system、user、params、`maxOutputTokens` 与期望章节 `sections`，改其中任何一项都要新建版本。
  `CI` 为真或给出 `--frozen-lock` 时锁被冻结，缺少条目也是配置错误：新版本或新样本先在本地运行一次，并提交 `prompts.lock.json`。
- 套件可选 `inputSchema`（`z` 从 `@product-res/evals` 导入），加载时逐个校验样本输入。

**三种模式**：

| 模式 | 参数 | 行为 |
|---|---|---|
| 回放（默认） | 无 | 只读录制，不访问网络、零费用；录制缺失记 `no-recording`、与当前渲染不符记 `stale-recording`，均计入失败，不回退到真实调用 |
| 真实 | `--live --budget-usd <美元>` | 调用真实模型，不写录制 |
| 录制 | `--record --budget-usd <美元>` | 调用真实模型，写入或覆盖生成与评委录制（`source: "recorded"`） |

- 生成与评委都以 `generateText({ instructions: system, prompt: user })` 调用：system 文本经 AI SDK 7 的 `instructions` 传入（`system` 参数已弃用；system 放进 `messages` 需 `allowSystemInMessages`，衍生项目自写脚本时曾因此被拒），各 Provider 收到同一形状，回放的模拟模型走同一路径。
- 真实与录制模式经 `defaultLanguageModelFactory` 调用，与线上同一套出口（direct / gateway），密钥取自根目录 `.env.local`（存在时由命令行用 `process.loadEnvFile` 加载）；错误信息中抹去 URL、凭据请求头的值与这些变量的字面值；
  录制只保存版本、渲染摘要、模型、输出、结束原因、用量与时间，不含请求头、端点或密钥。`CI` 为真时拒绝这两种模式，
  不提供绕过开关；需要在流水线中跑真实评测时，由项目另建手动触发的工作流。
- **预算**：真实与录制模式要求用到的模型两项单价都大于 0。每次调用（含评委）发出前估算上限 = 输入 token 估算 × 输入单价
  + 最大输出 × 输出单价（输入按码点 × `tokensPerChar` 加每条消息开销保守估算；评委另计评分标准与 JSON schema，最大输出取 `judge.maxOutputTokens`，缺省 4096；推理模型的 reasoning token 计入该上限，因此估算已覆盖思考开销）。
  已花费 + 在途预留 + 本次估算超过 `--budget-usd` 时不发出，本样本与之后未开始的样本记为 `skipped-budget`，退出码 3；并发时先预留再调用。
  调用后按实际用量结算，用量缺失按估算、失败按预留额记账；实际费用超过预留或已花费达到上限时立即触顶，不再发出新调用。
  **保证**：没有一次调用会在其保守估算放不进剩余预算时发出；总费用可能略超上限，超出部分不超过触顶时在途调用的估算误差之和。回放报告给出「按录制用量估算的真实运行费用」，用于决定预算；
  报告中的「实际 / 估算输入 token」比值可用来调整 `tokensPerChar`。

**评委**：套件的 `judge: { model, rubric, maxOutputTokens?, thinking? }` 中，`maxOutputTokens` 为评委输出上限（正整数，缺省 4096，早期固定 1024 时推理模型会在输出 JSON 前耗尽）；`thinking` 缺省 `false`，评委模型的 Provider 可控时（经 `resolveTextThinking` / `applyThinking`）显式下发关闭，设为 `true` 下发开启，不可控时不改请求。`rubric` 为 `{ version, instructions?, criteria: [{ id, description, weight? }], scale: { min, max } }`。
评委提示词由 `packages/evals` 内置，`temperature: 0`，按结构化 schema 输出每项分数与理由；各项归一到 0–1 后按权重得到样本总分。
输出无法解析或分数越界记为 `judge-error`（计入失败，不当作 0 分）。回放同样回放评委结果，被评输出或评分标准版本变化时视为录制缺失。
`--no-judge` 只跑确定性检查。LLM 评委本身有波动，以回放基线对比为准，真实模式的分数只作参考。

**确定性检查**：`checks.sections({ ordered? })`、`checks.length({ min?, max?, section? })`（按码点计）、
`checks.banned({ words?, patterns? })`、`checks.script({ lang?, minRatio? })`（汉字 / 拉丁 / 假名 / 谚文占比）、
`checks.chineseVariant({ variant?, maxCount? })`（简繁误用：内置约 500 个常用「仅繁体」字及对应「仅简体」字，
字表由 `packages/evals/scripts/chinese-variant-table.ts` 从 Unihan 生成）。自定义检查实现 `{ id, severity?, run(ctx) }`，
返回 `{ pass, detail?, severity? }`；`warn` 级失败只进报告。

**报告与基线**：

```sh
pnpm eval:prompts --suite report --prompt report@v4 --baseline report@v3   # 推荐：同次回放基线，免费可复现
pnpm eval:prompts --suite report --baseline-report <以前的 report.json>      # 适合对比真实模式结果
pnpm eval:prompts --suite report --record --budget-usd 0.5                 # 新版本先录一次，之后日常回放
```

- 报告写到 `$EVIDENCE_DIR/prompt-evals/<suite>/<UTC 时间戳>-<版本>-<模式>/`（未设置时为已忽略的 `test-results/evidence/`），
  含 `report.json` 与 `report.md`：版本与渲染摘要、模型、模式、git 提交、逐样本检查、评委分数与理由、用量、费用与汇总。
- 基线按样本 ID 对齐，列出分数差与检查结果变化；平均总分下降超过 `--max-regression`（缺省取套件 `regressionThreshold`，再缺省 0.05）判为回退。
  选择参数：`--prompt`、`--model`、`--judge-model`、`--samples a,b`、`--tag`、`--concurrency`（1–4）、`--frozen-lock`。

| 退出码 | 含义 |
|---|---|
| 0 | 全部通过，无回退 |
| 1 | 有 error 级检查失败、转换（`prepare-error`）、生成或评委错误、录制缺失或过期 |
| 2 | 配置错误：版本锁冲突或冻结时缺条目、真实模式缺预算或单价、CI 中开启真实调用、套件不存在（不写报告） |
| 3 | 预算触顶，部分样本被跳过 |
| 4 | 相对基线回退超过阈值 |
| 5 | 套件 `evaluateRun` 有门槛 `failed`、必需门槛 `incomplete`，或 `evaluateRun` 本身异常 / 返回不合法 |

同时出现多种情况时取最小的非零码。`pnpm eval:prompts` 不在 turbo 任何任务中；`packages/evals` 的单测（示例套件回放）随 `pnpm test` 运行，不发出真实调用。

#### 被评正文转换与评测后门槛（add-eval-extension-points）

两个可选扩展点，未声明时行为与上文完全一致。模板只负责执行时机、证据与退出码，领域规则与门槛数值都写在项目套件里。
执行顺序：生成或读取录制 → `prepareOutput` → 确定性检查 → 评委 → 内置回退判定与 `evaluateRun`。

**`prepareOutput`：评用户实际看到的正文**。线上保存的正文若在模型原文之上还有兜底处理（字形补正、按复算数据修正等），
在套件中声明同一个纯函数，检查与评委就都评处理后的正文：

```ts
import { defineSuite, type PreparedOutput } from '@product-res/evals'
import { deliveredText } from '../../apps/web/src/features/report/guard.ts' // 与线上共用的纯函数

export default defineSuite({
  // …
  prepareOutput: {
    version: 'guard.v4', // 转换逻辑一变就改版本：旧评委录制随之过期
    run({ rawOutput, sample, prompt }): PreparedOutput {
      const { text, stats } = deliveredText(rawOutput, sample.input, prompt.promptVersion)
      return { output: text, annotations: { glyphs: stats.glyphs, unresolved: stats.unresolved } }
    },
  },
})
```

- 回放、真实与录制三种模式走同一路径。hook 必须**无网络副作用、结果可重复**：需要的时间、复算数据从样本 `input`
  或提示词版本得出，不读当前时间或随机数。运行器对每个样本执行两次并比对，不一致即失败。
- hook 抛错、`output` 不是字符串、`annotations` 不是 JSON 可序列化的普通对象，或两次结果不一致时，样本记为
  `prepare-error`（退出码 1），不运行检查与评委，**不回退为原文**。
- 生成录制仍保存模型原文、用量与结束原因。评委录制的 `outputHash` 是**被评正文**的摘要，并记录 `prepareVersion`；
  回放时被评正文、评分标准版本或转换版本任一不符都判 `stale-recording`，需要重新录制评委。
  `--baseline` 的基线版本同样经过转换回放：新增或升级转换后**基线版本的评委也要重录**，否则基线样本全部过期、
  内置平均分对比没有可比样本。报告的 `baseline.scoredPairs`（两侧都有分的样本数）与 `baseline.baselineFailures` 会列出这种情况。
- 报告：样本的 `prepared` 记录 `{ version, rawSha256, outputSha256, rawChars, outputChars, changed, annotations }`，
  `outputChars` 为被评正文长度；报告目录写 `outputs/<id>.txt`（被评正文），改变时另写 `outputs/<id>.raw.txt`（原文）；
  `prepare-error` 的样本只写原文。

**`evaluateRun`：逐维度对比、绝对分与分位数门槛**。内置判定只比较加权总分均值；项目还需要别的门槛时，在套件中声明：

```ts
import { collect, defineSuite, mean, percentile, type RunGate } from '@product-res/evals'

export default defineSuite({
  // …
  evaluateRun({ samples, scope, candidate, baseline }) {
    const ids = samples.map((sample) => sample.id) // 用同一组 ID 收集候选与基线 = 按样本 ID 对齐
    const gates: RunGate[] = []
    for (const id of ['accuracy', 'tone']) {
      const now = collect(candidate, ids, (r) => r.judge?.criteria?.[id]?.score)
      const before = collect(baseline, ids, (r) => r.judge?.criteria?.[id]?.score)
      const missing = [...new Set([...now.missing, ...(baseline ? before.missing : ids)])]
      if (missing.length) {
        gates.push({ id: `${id}-vs-baseline`, status: 'incomplete', detail: `missing ${missing.join(', ')}` })
        continue
      }
      const delta = (mean(now.values) as number) - (mean(before.values) as number)
      gates.push({
        id: `${id}-vs-baseline`,
        status: delta >= -0.1 - 1e-9 ? 'passed' : 'failed', // 阈值与浮点余量由项目决定
        detail: `Δ ${delta.toFixed(3)}`,
        metrics: { delta },
      })
    }
    const durations = collect(candidate, ids, (r) => r.usage.generation?.durationMs)
    const p95 = percentile(durations.values, 95)
    gates.push(
      durations.missing.length || p95 === null
        ? { id: 'p95-duration', status: 'incomplete', detail: `missing ${durations.missing.join(', ')}` }
        : { id: 'p95-duration', status: p95 <= 240_000 ? 'passed' : 'failed', detail: `${p95} ms` },
    )
    // 筛选运行不能宣称全量门槛达成；required: false 的 incomplete 只进报告
    gates.push({ id: 'full-coverage', status: scope.filtered ? 'incomplete' : 'passed', detail: `${scope.selectedSamples} of ${scope.totalSamples}`, required: false })
    return { gates }
  },
})
```

- 调用时机：候选版本与基线（`--baseline` 同次回放，或 `--baseline-report` 旧报告）全部完成后调用一次；
  没有基线时 `baseline` 为 null。
- `candidate` / `baseline` 为 `{ promptVersion, source: 'run' | 'report', generator, judge: { …, rubricVersion }, results }`；
  `results` 包含选定范围内**每个**样本（含 `judge-error`、`no-recording`、`skipped-budget` 等），每项有 `status`、`checks`、
  `judge`（`criteria` 为各维原始分与理由，`error` 为失败原因）、`usage.generation`（`inputTokens`、`outputTokens`、`durationMs`）、
  `finishReason` 与 `prepared`。旧报告作基线时缺失的字段为空，交由项目判 `incomplete`。
- 辅助：`collect(group, ids, pick)` 返回 `{ values, missing, expected }`，缺样本或取值不是有限数都列入 `missing`，
  **不要在缩小的分母上宣称达成**；`percentile(values, p)` 为最近秩（排序后取第 `ceil(p/100 × n)` 个），`mean(values)`，空集合均返回 null。
- 门槛为 `{ id, status: 'passed' | 'failed' | 'incomplete', detail, required?, metrics? }`，`required` 缺省 true，
  `metrics` 须 JSON 可序列化。结果写入 `report.json` 的 `assessment` 与 `report.md` 的「Gates」小节。
  任一 `failed` 或必需 `incomplete` 以退出码 5 退出；它排在 1、3、4 之后，**不掩盖**检查 / 生成失败、预算触顶与回退。
  内置总分回退判定照常生效。hook 抛错或返回不合法时，报告记一个 `evaluate-run` 失败门槛，样本结果保留。
- 多个语言 / 产品组合、多个真实基线版本时，按组合拆成多个套件，或在 `evaluateRun` 中按样本 `tags`、`input` 字段自行分组判定；
  逐组与整批口径由项目决定并在门槛 `detail` / `metrics` 中写明范围与样本数。

**生成耗时与范围**：真实 / 录制模式实测每次生成耗时并写入生成录制的 `durationMs`；回放读取录制值，旧录制没有该字段时为空，
不用本机回放耗时代替。报告的 `scope` 记录 `{ totalSamples, selectedSamples, filtered, sampleFilter?, tag? }`，筛选运行时
`report.md` 标明「Scope: N of M samples (filtered …)」；`summary.expectedScores` 与 `scoredSamples` 并列，评委错误一目了然。

**评委失败不重试**：评委输出无法解析、缺评分项或越界时样本记 `judge-error`（退出码 1），不当作 0 分、不自动重试；
需要补分时用 `--record --samples <id> --budget-usd …` 显式重录该样本。

## 4. 图片 / 视频：异步任务

### 服务商注册表与接口

模型注册表 `ai_model` 负责模型参数、套餐可见性和计价；[媒体服务商注册表](../packages/ai/src/media/registry.ts)负责执行能力。`ai_model.provider` 对应定义的 `id`，定义包括 `synchronous`、`supportedKinds`、`outputHosts`、`isConfigured(env)` 与 `create(env, { modelId })`。任务保存服务商与 `providerModelId` 快照，运行时按快照重建实例，不依赖 isolate 内的作业映射。

| 服务商 ID | 能力 | 配置检查 | 产出与下载白名单 |
|---|---|---|---|
| `fal` | 异步图片 / 视频 | `FAL_KEY` | HTTPS URL；精确主机 `fal.media`、`v3.fal.media`、`v3b.fal.media` |

接口的完整类型见 [provider.ts](../packages/ai/src/media/provider.ts)：

```ts
interface MediaSubmitInput {
  modelId: string
  params: Record<string, unknown>
  webhookUrl?: string
  idempotencyKey: string // ai_task.provider_request_key；不支持时实现方忽略
}

interface MediaProvider {
  readonly id: string
  readonly capabilities: { readonly idempotentSubmit: boolean }
  submit(input: MediaSubmitInput): Promise<{ jobId: string; sync?: MediaResult }>
  getStatus(jobId: string): Promise<MediaStatus>
  parseWebhook(req: Request, rawBody: string): Promise<MediaWebhook>
  cancel?(jobId: string): Promise<void>
}

interface SyncMediaProvider {
  readonly id: string
  readonly capabilities: { readonly synchronous: true; readonly idempotentSubmit: boolean }
  run(input: MediaSubmitInput): Promise<MediaBinaryResult>
}

type TaskMediaProvider = MediaProvider | SyncMediaProvider
```

`MediaResult` 包含下载地址、MIME、可选宽高 / 视频时长，以及可选 `usage.images` / `usage.seconds`；`MediaStatus` 为 queued / running / succeeded（带结果）/ failed（带错误）。`MediaWebhook` 始终带 `jobId`，可以带结果、错误或仅通知查询原作业。同步 `MediaBinaryResult` 的输出为 `Uint8Array` / `ReadableStream<Uint8Array>` 与 MIME，不能作为 Workflow step 返回值。

### fal.ai 实测与能力标记

[Queue](https://fal.ai/docs/documentation/model-apis/inference/queue) 和[请求头](https://fal.ai/docs/documentation/model-apis/common-parameters)文档没有承诺客户端提交去重。**2026-10-12（Asia/Taipei）实测**：向 `fal-ai/flux/schnell` 连续发送完全相同的请求体与同一个 `Idempotency-Key`，返回两个不同的 `request_id`，主动查询确认两个作业都完成。因此该端点在本次测试中未按此请求头去重；这不证明任何其他未测试机制均无效，但不足以承诺安全重提，当前继续设 `idempotentSubmit=false`，实现忽略提交键且不自动重试。

真实录制见 [夹具与录制说明](../packages/ai/src/media/fixtures/README.md)：提交 HTTP 200；运行状态 HTTP 202 且 `logs=null`；完成与图片结果 HTTP 200；成功回调 `status='OK'` 且 `error=null`。回调通过临时接收器取得，原始请求体在脱敏前用 fal 公开 JWKS 验证 Ed25519 签名；离线测试对脱敏后的真实载荷重新签名，不能把测试签名称为 fal 原签名。两个 512×512 图片及一次 480p 视频提交按公开价格保守估算最多 $0.056，未部署 staging。

视频仅提交后立即 PUT 取消，返回 HTTP 202 `CANCELLATION_REQUESTED`；取消后的即时查询仍为 `IN_PROGRESS`，未获取视频结果。202 只代表接受取消请求，不保证已停止推理或免费；已完成图片的取消实测返回 HTTP 400 `ALREADY_COMPLETED`。视频结果、生成失败与异常回调仍由官方文档构造的补充夹具覆盖，不作为真实录制证据。

`createFalMediaProvider({ apiKey, modelId, fetch })` 按任务模型创建实例，查询 / 取消使用原始 `request_id`，队列路径按基础模型去掉子路径。`FalProviderError.submissionOutcome` 区分明确拒绝与可能已受理。回调按[官方验签协议](https://fal.ai/docs/documentation/model-apis/inference/webhooks)验证 Ed25519、原始请求体 SHA-256 与 ±5 分钟时间窗，JWKS 最多缓存 24 小时；`payload_error` 通知只返回 `jobId`，调用方查询原作业。视频未回报时长时不提供 `usage.seconds`，不能用推理耗时计费。

### Workers AI 同步产出路径

[Workers AI Provider](../packages/ai/src/media/workers-ai.ts) 通过 `AI.run(providerModelId, params)` 调用图片模型：Flux 的 base64 与 SDXL 等模型的二进制流都根据文件头识别 JPEG / PNG / WebP / GIF，返回一张图片的用量。web / jobs 均声明 `AI` 绑定，web 用它检查是否已配置，实际推理由 jobs 执行；无外部密钥，费用计入 Cloudflare 账号。

用户仍通过同一个任务接口立即获得 `taskId`。Workflow 的 `submit` step 调用 `run` 后，在**同一个 step** 内按确定性 R2 key 写对象与 `file` 记录，并保存结果和用量，只返回文件 ID，然后直接进入 `settle-and-notify`；不进入回调、等待或轮询。同步提交 step 超时 15 分钟；只有 Provider 标为瞬时的失败（Workers AI 官方错误码 3007 超时、3008 中止、3040 容量不足）按 10 秒起指数退避最多重试 2 次，其余失败以 `NonRetryableError` 带原错误码立即终止，最终失败全额释放。绑定错误只保留错误名与数字码（如 `AiError 8007`）写入任务错误信息与 `ai.media.sync_submit_failed` 日志，上游描述可能回显提示词，不保留。8007（输入被判定为 NSFW）不重试：2026-10-13 实测同一无害提示词在 REST API 上时而成功时而 8007，但重试内容审核拒绝等同绕过审核。重放可能重新推理，但覆盖同一对象并复用文件记录，不重复文件或积分结算；`idempotentSubmit=false` 不代表推理本身可去重。转存同样检查 MIME、单文件大小和空间配额，字节不会跨 step 传递。

### Workflow

[index.ts](../apps/jobs/src/index.ts)负责绑定、Provider 创建和存储依赖，[media-runner.ts](../apps/jobs/src/workflows/media-runner.ts)执行持久步骤。异步流程为：

```text
load-task → submit → check-callback
  → 提交结果不确定：uncertain-wait-until → uncertain-check-callback
    → wait-uncertain-callback → uncertain-recheck-callback（仍无回调则失败退款）
  → 若无结果：wait-media-done → recheck-callback → poll-N / poll-delay-N
  → persist → settle-and-notify
失败 → fail-and-notify；已终态 → 停止后续业务步骤
```

- **提交幂等**：创建任务时 `provider_request_key=task.id`，Workflow 实例 ID 也为 `task.id`。`submit` 先读库，已有 `provider_job_id` 直接复用；外部调用前持久化 `output.submissionAttempted`，防止非幂等服务商在受理与 jobId 落库之间崩溃后再次提交。拿到 jobId 立即落库并置 running。明确拒绝会清除此标记，允许 step 重试。
- **不确定提交**：不支持幂等时的超时、连接中断、5xx 或响应丢失（以及重放时发现已尝试提交却没有 jobId）不重提，也不立即退款：任务保持 `running`，`error_code='MEDIA_SUBMISSION_UNCERTAIN'` 作为「提交确认中」标记，预扣保留。Workflow 在运行时设置 `ai.mediaUncertainWaitSeconds`（默认 3600 秒，且不超过任务 2 小时期限）内等待回调；回调入口验签后写入回调中的作业 ID 并清除标记，Workflow 采用该 ID 走正常的查询、转存与结算。超时仍无回调时以 `MEDIA_SUBMISSION_UNCERTAIN` 失败并全额退回。验收故障模型改用其 `initialWaitMs`（5 秒）作为等待时限，且不采用晚到回调。
- **回调与事件**：保留 `check-callback` 与 `recheck-callback`。`sendEvent` 的 `{ taskId }` 只唤醒 Workflow，结果始终重新读取已落库的 `callback_payload`；通知失败也能在等待超时后恢复。已收到仅含 jobId 的通知时直接查询原作业，不再等满 15 分钟。
- **转存 R2**：使用确定性 key `ws/{workspaceId}/ai/{taskId}/{输出序号}`，重放覆盖同一对象并复用文件记录。带 `Content-Length` 时经 `FixedLengthStream` 流式写入；无长度时用 multipart（除最后一片外每片至少 5 MB），累计超上限即中止。限制类型与精确主机白名单，单文件上限为 100 MiB。空间配额在提交前检查；转存后才超出配额（提交时与当前权益取较小值）时仍保存产出并按成功结算，`persistMediaOutputsWithQuota` 返回 `overQuota`，兼容入口 `persistMediaOutputs` 记 `storage.media.over_quota` 日志；此后的上传与提交因配额已满被拒绝。
- **结算与终态**：成功按任务定价快照结算，媒体用量以请求参数上限封顶；失败全额释放；取消按下节规则结算。结算与站内通知使用共用 `settleMediaTask`；每个步骤前及缓存步骤返回后自检终态，晚到 Workflow 不重复扣费。

### 用户取消

`POST /api/ai/tasks/:id/cancel` 只允许提交者调用，计费类型写入 `ai_task.cancel_billing`：

| 服务商状态 | 结算 | `cancel_billing` |
|---|---|---|
| 尚未开始（无 jobId 且未尝试提交；fal `IN_QUEUE`） | 全额退回，不占用免费次数 | `free_unstarted` |
| 已开始，且该工作区从未用过免费取消 | 全额退回 | `free_started` |
| 已开始，免费次数已用完 | 按定价快照全价（等于预扣额）扣费 | `charged` |

- **判断已开始**：有 jobId 时查询服务商状态（fal `IN_PROGRESS` 或已完成视为已开始）；查询失败、已尝试提交却没有 jobId（提交在途或提交确认中）以及同步 Provider 运行中均按已开始处理，以平台风险最小为准。
- **流程**：先查状态，再尽力通知服务商取消，然后在 ws → credits → task 锁内结算。免费次数在同一把锁内读取，部分唯一索引 `(workspace_id) where cancel_billing='free_started'` 在数据库层保证每个工作区终身一次。重复调用直接返回已结算结果，不重复退款或扣费；外部取消失败保留 `MEDIA_CANCEL_PENDING`，重试只补外部取消。
- **预览**：`GET /api/ai/tasks/:id/cancel?workspaceId=` 只读返回 `started`、`charged`、`credits` 与 `freeStartedRemaining`。前端先展示说明、确认后才执行；执行结果以服务端返回为准，与预览不一致时提示用户。

### 等待与轮询参数

合法故障任务把版本 1 固定策略及管理员授权结果存入 `input.acceptanceFault`，后续修改或停用
模型不改变原任务。执行证明放在独立的 `input.acceptanceFaultProof`，空间→任务锁下局部合并，
不进入 Provider 参数，也不依赖结算时覆盖的 output。fal 专用输入固定 square、一张；所有 hold
仍在 deadline 后 10 分钟到期，正常任务的 2 小时 deadline、15 分钟等待及重试参数保持。

| 故障模式 | 固定时间与触发方式 | 证据边界与结果 |
|---|---|---|
| `workers-error` | 合成不可重试 `WORKERS_AI_GENERATION_FAILED` | 不调用 AI 绑定，不产生字节/文件；failed、全退 |
| `workers-timeout` | 60 秒 deadline；running 状态持久 sleep 至 deadline，再由 active 检查超时 | 不调用 AI，不伪造图片或直接结算；证明任务截止与退款，不声称真实服务挂起 |
| `fal-callback-lost` | 20 分钟 deadline；真实 submit 去掉 webhook；wait 5 秒后查询原作业 | 一次真实 submit、真实 request ID、pollCount>0、无 callback；成功产出与消费各一份 |
| `fal-callback-early` | 20 分钟 deadline；真实 webhook；jobId 落库后在正常 check 前最多等 10 分钟，每 2 秒持久 sleep | 验签回调先落库，再记录 callbackCheckedAt；未观察到则失败，不能用普通轮询成功代替 |
| `fal-submit-response-lost` | 真实 submit 去掉 webhook；ID 写证明后抛 ambiguous 错误 | 业务 jobId 留空，等待 `initialWaitMs` 后按 UNCERTAIN 全退且不重提；证明 ID 结算后仍存在 |
| `fal-provider-error` | 20 分钟 deadline、wait 5 秒；查询真实原作业后包装成确定失败 | 原失败全退；真实成功回调经验签后被忽略，不能恢复成功 |
| `fal-timeout` | 60 秒 deadline、wait 5 秒；查询真实原作业后包装 queued，睡眠截短到剩余 deadline | 实际到 deadline 才超时全退，不能产出图片；晚到结果/重放不重复结算 |

三个失败 fal 模式按证明中的原 request ID 尽力取消，记录 `cancellation-requested`（仅受理）、
`already-terminal`（取消失败后原 Provider 查询已 succeeded/failed）或 `unconfirmed`。
202 不证明推理已经停止，也不免除服务商计费；仍 queued/running、取消与查询失败均需人工核验，

> - 事件早到时平台会缓冲，至少 60 分钟后仍可送达；这是 Phase 0 实测结论，本轮 fal 录制不重新证明平台事件保留上限。

### 回调入口
`POST /api/webhooks/media/:provider?task=:id&sig=:hmac`
- 用自签 HMAC（taskId + secret）校验 URL，外加 provider 自身的签名校验（如有）。
- **提交确认中的任务**：任务处于 `MEDIA_SUBMISSION_UNCERTAIN` 标记且没有 jobId 时，任务 HMAC 与服务商签名都通过即接受，并写入回调中的作业 ID、清除标记；已有 jobId 时回调必须与之相同。
- **晚到回调**：任务已终态（成功、失败或取消）后到达的回调只记 `ai.media.callback_after_terminal` 日志，不写库、不唤醒 Workflow，已结算结果不变。
- **先落库，再通知**：把解析后的结果写入 `ai_task.callback_payload`（仅当为空时写入，幂等），再 `env.AI_MEDIA_WORKFLOW.get(ai_task.workflow_instance_id).sendEvent({ type: MEDIA_DONE_EVENT, payload: { taskId: ai_task.id } })`。`sendEvent` 失败不影响返回 200——Workflow 会在 `check-callback` / 超时后的 `recheck-callback` 中读到结果。

### 并发与防滥用
- 并发数检查与创建任务、预扣必须在**同一事务**中，并先取空间级事务锁，否则两个同时到达的请求都能通过 count 检查：
  ```sql
  BEGIN;
  SELECT pg_advisory_xact_lock(hashtextextended('ws:' || $ws, 0));   -- 同一空间的提交串行化，事务结束自动释放
  SELECT count(*) FROM ai_task WHERE ws = $ws AND status IN ('queued','running');   -- 须 < maxConcurrentTasks
  INSERT INTO ai_task (...);   -- 含 pricing 快照、provider_request_key、deadline_at
  -- hold()：锁批次并预扣（同一事务）
  COMMIT;
  -- 事务提交后再启动 Workflow；启动失败则将任务标记 failed 并 release
  ```
  Advisory lock 是事务级的，经 Hyperdrive 已实测可用：后到者等待先到者结束，提交、回滚或 Worker 中途结束后锁均释放（Phase 0 任务 7.1，见 `docs/07-infrastructure.md` §2「事务与锁」）。
- 存储配额在同一事务内、预扣之前检查：空间用量已达到或超过 `storageGb` 时返回 `STORAGE_QUOTA_EXCEEDED`（403），不预扣、不提交。
- `RL_AI` 限流绑定按 workspace + user 限制提交频率，用于防刷和削峰。
- 限流绑定按数据中心分别计数、不精确，**不能用来实现配额**：需要精确保证的限制（并发任务数、积分余额、每日额度等）一律在 Postgres 事务里检查。
- 可选内容审核：提交前对 prompt 做审核（服务商自带或单独调用）。

### 安全下载
`copyOutputsToR2` 只允许从该 provider 的已知域名下载（防 SSRF），限制最大文件大小与 MIME 类型。

## 5. 文件与输入素材

- 图生图 / 图生视频的输入，直传 R2 分三步：
  1. `POST /api/files/uploads`（声明 `mime`、`size`）：服务端校验 MIME 白名单、单文件上限、`已用 + size ≤ storageGb`，插入 `file(status='pending')`，返回预签名 PUT URL（有效期 10 分钟，签名包含 `Content-Type`）。
  2. 前端直传 R2。
  3. `POST /api/files/:id/complete`：服务端 `R2.head()` 取对象**真实**大小与类型，与声明不符或超出配额 → 删除对象、标记失败；通过则置 `status='ready'`。
  - 原因：R2 的预签名 PUT 无法限制上传体积（S3 的 POST policy `content-length-range` 在 R2 不可用），只能上传后校验。提交任务时只接受 `status='ready'` 的 `fileId`；Cron 清理超过 1 小时仍为 `pending` 的记录及对象。
  - 服务端给 provider 生成短期可读 URL。
- 产出文件访问：通过 `/api/files/:id` 鉴权后 302 到短期签名 URL；公开分享作为可选功能（`file.public_token`）。
- 预签名 URL 需要 R2 的 S3 兼容 API 凭证（`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`，令牌权限限定到 `FILES` 桶），用 `aws4fetch` 在 Worker 内签名。
- 配额：按 `sum(file.size) where status='ready' and deleted_at is null` 对照权益 `storageGb`。
