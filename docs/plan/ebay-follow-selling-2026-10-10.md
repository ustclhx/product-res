# eBay 跟卖选品平台：流程与实施方案

更新：2026-10-10。状态：方案已讨论确认，尚未开始实施。本文是新仓库建立后编写 OpenSpec proposal 的依据。

原选品工作流代码、文档和调研已冻结在 `frozen/selection-workflow-pilot` 分支；本文引用的 `app/`、`docs/pilot/`、`research/` 等路径均指该分支。

## 0. 背景与已确认的决定

现有 product-res 是一个通用的选品审批流程（项目/标准 → 候选 → 补证 → 评估 → 决策 → 验证 → 复盘 → 反馈），流程重、概念多，并且缺少“数据采集 → 线索发现 → 成本核算”这一段，难以支撑选品的精准性。决定如下：

| 事项 | 决定 |
|---|---|
| 现有流程 | **冻结**：不再扩展。旧 pilot 继续在 ECS 上运行，新系统上线后再下线 |
| 业务主线 | 跟卖：用 eBay 官方数据观察同质化店铺的新品和销量，结合开学、节假日等节点发掘线索，再对比供应商价格核算成本 |
| 框架 | 方案 A：用 `../saas-template` 的 `create-project` 生成**新仓库**；等模板就绪后再建，现在不操作 |
| 部署 | A2：全部服务运行在新加坡 ECS 上。Node 部署目标与部署方案由 saas-template 负责构建，**不在本方案范围内** |
| 模板模块 | 保留 auth、admin、db、jobs、ai、ui、shared、config；关闭 billing、credits、entitlements、营销页、博客、i18n、SEO、waitlist、newsletter、public-api |
| 账号 | 团队共用一个账号；平台不做分工、指派，也不记录“谁做的” |
| 类目与物流 | 不锁定类目；选品方向、物流方案（直发 / 海外仓）都是可增删改的配置 |
| eBay 额度 | 按每天 5000 次调用设计，安全线 4500，绝不超额 |
| eBay 账号 | 目前还没有，按“会有 Production 账号”设计 |
| 季节数据 | DataForSEO（Google Trends + 关键词月搜索量历史） |
| 风险提示 | 同款同货源和同款微改良两种做法都提示；本地品牌库 + VeRO 名单（人工维护）+ 检索链接，不接付费商标/专利接口 |
| 算法 | 有选品算法、回测、置信度和算法准备度；权重等权起步，团队可调 |
| 命中标准 | 默认推荐后 30 天内商品簇销量增量 ≥ 30 件，且竞品中位价跌幅 ≤ 15%；可配置 |
| Terapeak 导入 | 模板 A（汇总级）和模板 B（listing 明细级）都要做，但 **hold**，等与合作方沟通数据来源和导入方式 |

## 1. 设计原则

1. **系统先给线索，人只做判断。** 数据由系统每天自动采集；人每天只花 15–30 分钟看线索、做决定。
2. **一条线索只有一个状态。** 不设标准版本、评估快照、多级审批。
3. **钱算清楚再动手。** 判断跟不跟卖的唯一硬门槛是利润。
4. **从节点倒推时间。** 系统根据节点日期倒算最晚决定日，提醒人在窗口内做决定。
5. **证据不足要如实显示。** 缺失不补零；冷启动期不假装有可信推荐。

## 2. 总体流程

```
[0 配置]  选品方向（类目/关键词/店铺池）· 物流方案 · 成本参数 · 节点日历 · 品牌库
   ▼
[1 采集]  每日自动，受额度预算约束：eBay 店铺快照 + DataForSEO 季节曲线
   ▼
[2 算法]  信号计算 → 硬门槛 → 综合评分 → 置信度
   ▼
[3 线索]  人：关注 / 忽略 / 稍后（每条带风险提示和置信度）
   ▼
[4 核算]  供应商 × 物流方案 × 跟卖方式，并排对比利润
   ▼
[5 决定]  跟卖 / 放弃（选原因）
   ▼
[6 验证]  影子推荐自动打标签 + 实际跟卖回看 → 回测 → 校准算法和置信度
          └──────────────── 反馈回 [2] ────────────────┘
```

线索状态：

```
新线索 → 关注 → 核算中 → 跟卖 → 已上架 → 已回看
   ├──→ 稍后（到期回到新线索）
   └──→ 忽略（选原因）        └──→ 放弃（选原因）
```

所有推荐不论人有没有处理，都自动进入影子回测。

## 4. 采集

### 4.1 eBay 额度预算（硬上限 5000 次/天，安全线 4500）

| 任务 | 方式 | 估算每日调用 |
|---|---|---|
| 店铺新品 | 每家店按“最新上架”搜索 1–2 页（`search` + `filter=sellers:{…}` + `sort=newlyListed`） | 30 家 × 2 = 60 |
| 热点 listing 快照（近期有动销或命中线索） | 每日一次，批量查询，每次 20 个（`getItems`） | 2000 ÷ 20 = 100 |
| 普通 listing 快照 | 每 3–7 天轮询一次 | ~100 |
| 方向扩展（发现新的同质店铺和商品） | 类目 + 关键词搜索 | ~200 |
| 新 listing 详情补全 | 单个查询（`getItem`） | ~500 |
| **合计** | | **~1000** |

- 每次调用前在数据库事务里预扣额度，扣不到就顺延到次日，从机制上保证不超额；同时记录 eBay 返回的限额信息用于对账。
- **待实测（M1 第一项）：** `getItem` 和 `getItems` 是否返回 `estimatedAvailabilities[].estimatedSoldQuantity`。现有调研（`research/ebay-dtc-data-sources-2026-09-20.md`）认为 Browse 拿不到销量，与这一字段的存在相矛盾，必须用 Production 凭据确认。
  - 如果只有 `getItem` 返回，热点快照改为逐个查询，约 2500 次/天，仍在额度内，但轮询档位要收紧。
  - 如果都拿不到，用可售量的减少来近似销量，并下调“数据覆盖”维度的置信度。
- eBay 历史成交接口（Marketplace Insights）不对新用户开放；销量增量只能靠每日快照做差分得到。

### 4.2 季节数据（DataForSEO，不占 eBay 额度）

- Google Trends 5 年周度曲线，以及关键词月搜索量历史。
- 每周更新一次。

## 5. 选品算法

### 5.1 信号（每个商品簇一组分数，0–100）

| 维度 | 计算 | 含义 |
|---|---|---|
| D 需求动量 | 商品簇 7 天销量增量，以及相对 30 天均值的加速度 | 现在卖得动吗 |
| A 扩散度 | 14 天内上架同簇商品的对标店铺数，以及上新的时间集中度 | 同行在不在跟 |
| T 季节匹配 | 目标销售窗口内的季节指数（窗口热度 ÷ 全年基线）× 历年规律稳定性 | 卖的时候赶上高峰吗 |
| W 时间可行性 | 最晚决定日 − 今天（按物流方案和跟卖方式计算） | 来得及吗 |
| P 利润空间 | 竞品中位价下、各物流方案中最优的估算毛利率 | 有钱赚吗 |
| C 竞争压力（扣分） | 卖家数增长、最低价下滑、头部卖家份额 | 是否陷入价格战 |
| R 风险（门槛 + 扣分） | 见第 6 节 | 能不能做 |

最晚决定日的倒推：

```
最晚决定日 = 节点销售开始日 − 物流时长 − 采购时长（微改良再加打样天数）− 上架准备
例：返校季 7/15 起卖，海运海外仓 35 天，采购 10 天，上架 3 天 → 5/28 前必须决定
```

### 5.2 打分流程

1. **硬门槛**（不通过就不推荐，但可以在列表中查看原因）：
   - 风险等级为“高”（命中品牌黑名单或受限类目）；
   - 所有物流方案下 W < 0（已经来不及）；
   - 所有物流方案下 P < 毛利率底线。
2. **综合分** = w_D·D + w_A·A + w_T·T + w_P·P − w_C·C − w_R·R。等权起步，团队可调；回测样本足够后，用历史标签拟合权重（先用逻辑回归这类可解释模型），由团队确认后启用。
3. **置信度**（见第 9 节）与综合分分开显示。列表按“综合分 × 置信度”排序；高分低置信标为“值得关注但证据不足”。

### 5.3 商品簇归并

依次使用：GTIN/ePID 精确匹配 → 标题向量相似 → 图片相似。每个成员记录归并置信度；人可以手动拆分或合并商品簇，这些修正也作为以后的训练样本。AI 用量走 `packages/ai` 的预算。

## 6. 侵权与风险提示

| 风险类型 | 检测方式 | 同款同货源 | 同款微改良 |
|---|---|---|---|
| 品牌/商标 | Brand 属性不是 Unbranded/Generic；标题命中本地品牌库；VeRO 名单 | 高 | 中（标题和包装去品牌后降为低） |
| 外观/设计专利 | 同簇只有一个主卖家、款式独特、卖家有品牌店 → 提示人工检索，附 Google Patents 链接 | 中 | 视改动程度 |
| 图片/文案版权 | 提醒必须自拍或使用供应商授权图 | 提示 | 提示 |
| 类目准入/认证 | 受限类目、儿童用品（CPC/CPSIA）、带电、食品接触等，按规则表匹配 | 按规则 | 按规则 |
| 物流禁运 | 商品属性与物流方案的禁运属性冲突 | 该方案不可用 | 同左 |
| 价格战 | 来自 C 竞争压力 | 同款更容易被卷 | 有差异化缓冲 |

微改良的代价在核算中自动体现：提前期加上打样天数，成本加上改款费分摊。

## 7. 核算

- 每个商品可以挂多家供应商：1688 或其他链接，加手填报价（单价、数量阶梯、MOQ、重量和尺寸）。报价可信度分两档：公开价、已确认报价。
- 对比矩阵：供应商 × 物流方案 × 跟卖方式，每格显示落地成本、保本价、竞品中位价下的毛利率、按该方案倒推的最晚决定日。系统高亮最优组合，人选一个组合做决定。

| 成本项 | 来源 |
|---|---|
| 采购价（计划数量对应的阶梯价） | 报价 |
| 头程和尾程运费 | 物流方案 × 重量体积 |
| eBay 成交费、固定费、广告费 | 成本参数 |
| 退货预留 | 成本参数 |
| 微改良的改款费分摊 | 跟卖方式设置 |
| 竞品价格分布（最低价、中位价、销量最高那家的价格） | 采集数据 |

决定：

- **跟卖**：填首批数量、目标售价、计划上架日。
- **放弃**：选原因（利润不够 / 竞争太多 / 时间来不及 / 货源不行 / 侵权风险 / 其他），以后用于调整打分。
- 跟卖后 30 天提醒回看一次：录入实际销量和售价，与当初的判断对比。

## 8. 回测与验证

### 8.1 数据来源

| 数据 | 能否回测 | 方式 |
|---|---|---|
| 季节曲线 | 从第一天就能 | 5 年 Trends 滚动验证：用前 N 年预测下一年的高峰时间和幅度 |
| eBay 信号（D/A/C） | 需要积累 | 上线即开始影子推荐：冻结当时的分数、输入和权重版本，在 T+14、T+30、T+60 天用快照自动打标签 |
| 现存 listing 的上架日期 + 累计已售 | 弱历史 | 粗估过去 90 天的平均速度；有幸存者偏差，只作冷启动参考 |
| 实际跟卖结果 | 最真实但样本少 | 30 天回看时录入 |
| Terapeak 导入 | hold | 见第 12 节 |

### 8.2 命中标准

- 推荐后 T+30 天：商品簇销量增量 ≥ X（默认 30 件），并且竞品中位价跌幅 ≤ Y%（默认 15%），记为“命中”。
- 季节类推荐另外看高峰周预测误差 ≤ 2 周。
- X、Y 和观察窗口都可配置。

## 9. 置信度与算法准备度

### 9.1 单条线索的置信度

| 维度 | 衡量什么 | 示例指标 |
|---|---|---|
| ① 数据覆盖 | 证据量够不够 | 快照天数、同簇 listing 数、覆盖店铺数、能否拿到已售量字段 |
| ② 数据新鲜度 | 是不是最新的 | 最近一次快照距今小时数 |
| ③ 信号一致性 | 独立信号是否互相印证 | D、A、T 中同时为正的个数 |
| ④ 归并可信度 | 是不是真的同款 | 簇内标题、图片、属性的相似度 |
| ⑤ 季节规律稳定性 | 往年规律靠不靠谱 | 历年曲线相关系数、高峰周的年际波动（Terapeak 数据到位后叠加站内曲线交叉验证） |
| ⑥ 成本确定性 | 账算得准不准 | 报价类型、物流模板完整度、费率是否已配置 |
| ⑦ 时间余量 | 来不来得及 | 剩余天数 ÷ 所需提前期 |
| ⑧ 竞争稳定性 | 价格和卖家数是否剧烈变动 | 价格波动率、卖家数增速 |
| ⑨ 历史命中率 | 同类推荐过去准不准 | 同信号类型、同方向的回测命中率，用 Wilson 置信下界（样本少时自动打折） |

### 9.2 算法准备度（某个方向、某类信号整体能否信任）

| 等级 | 条件（初始值，可调） | 界面表现 |
|---|---|---|
| 冷启动 | 影子推荐样本 < 20 | 只展示信号，不给综合推荐，标注“未验证” |
| 观察期 | 样本 20–50 | 展示推荐，置信度上限为“中” |
| 可用 | 样本 ≥ 50，命中率下界 ≥ 基线 | 正常推荐 |
| 可信 | 样本 ≥ 100，权重已校准，最近 3 个月命中率稳定 | 可作为优先级依据 |

基线是同方向随机抽取新品的命中率；推荐命中率必须明显高于基线，才说明算法有用。准备度界面分别显示“实测样本数”和“导入样本数”（后者等 Terapeak 导入启用后才有）。

## 10. 页面

1. **今日线索**（首页）：排序列表、风险标签、置信度、节点倒计时。
2. **选品方向**：方向的增删改，以及每个方向的店铺池和新品流。
3. **商品簇详情**：各家店铺和价格、销量曲线、季节曲线叠加、风险明细、手动拆分/合并。
4. **核算**：供应商 × 物流 × 跟卖方式的对比矩阵和决定。
5. **回测与准备度**：各方向、各信号的命中率曲线和准备度等级。
6. **设置**：物流方案、成本参数、节点日历、品牌库与风险规则、打分权重和阈值、额度用量。
7. `/admin`：沿用模板。

## 12. Terapeak 历史数据导入（hold）

模板 A 和 B 都要做，等与合作方沟通数据来源和导入方式后再定。目前的设想，供以后讨论：

- 平台定义自己的标准模板，不依赖 Terapeak 原始格式；导入时自动识别列名，识别不了的手动对应。
- **模板 A（汇总级，用于站内季节曲线）：** query、category_id、marketplace、period_start、period_end、total_sold、avg_sold_price、currency，可选 total_sellers、sell_through_pct、avg_shipping、free_shipping_pct。
- **模板 B（listing 明细级，用于历史商品簇和打标签）：** item_id 或 url、title、avg_sold_price、currency、total_sold（指查询时间窗口内的成交量）、query/period_start/period_end（导入时必须补上），可选 item_sales、shipping、last_sold_date。
- 流程：上传或粘贴 → 选模板并映射列 → 补填方向、查询词、时间窗口等上下文 → 预览校验（缺失保持为空，不补零；重复导入保留历史、以最新为准）→ 确认导入并标记来源 → 自动重算季节曲线和历史回测。
- 来自 Terapeak 的回测样本单独标注，权重低于平台自己的影子推荐。
- 待确认：Terapeak 是否能导出、导出列名、趋势图能否导出逐周数据。

## 13. 分期（每期对应一个 OpenSpec change）

| 期 | 内容 | 验收标准 |
|---|---|---|
| M0 | 用模板生成仓库，关闭不需要的模块，部署到 ECS，共享账号登录 | 能登录，健康检查通过，定时任务能写库 |
| M1 | 选品方向和店铺池配置；eBay 采集、快照、额度账本 | 第一项：实测 `estimatedSoldQuantity`；连续 7 天快照不超额 |
| M2 | 商品簇归并、信号、打分、风险提示、今日线索页；DataForSEO 季节曲线和节点倒推 | 线索列表可用，每条能说明推荐理由 |
| M3 | 供应商报价、物流方案、核算矩阵、跟卖/放弃决定 | 一条线索能从发现走到决定 |
| M4 | 影子推荐、自动打标签、置信度、准备度页面、权重调节 | 推荐自动积累标签，准备度等级正确流转 |
| Hold | Terapeak 导入（模板 A 和 B） | 等合作方确定数据来源 |

M1 上线后应尽快持续运行：回测样本只能靠时间积累，M2–M4 可以在已有数据上迭代。

## 14. 风险

| 风险 | 应对 |
|---|---|
| eBay Production 账号的审批或合同门槛 | 账号申请与 M0 并行，尽早启动 |
| `estimatedSoldQuantity` 拿不到或覆盖不全 | 用可售量减少近似，下调数据覆盖置信度 |
| 商品簇归并不准导致信号失真 | 显示归并置信度；支持手动拆分/合并并作为训练样本 |
| 冷启动期没有可信推荐 | 界面如实显示“冷启动”，只展示信号 |
| 模板 Node 部署目标未就绪 | 作为 M0 的前置条件，新仓库在此之前不建立 |
| 季节曲线是搜索热度，不等于 eBay 成交 | 只作为 T 维度输入；Terapeak 数据到位后交叉验证 |
