## 0. 背景与已确认的决定

现有 product-res 是一个通用的选品审批流程（项目/标准 → 候选 → 补证 → 评估 → 决策 → 验证 → 复盘 → 反馈），流程重、概念多，缺少“数据采集 → 线索发现 → 成本核算”这一段，难以支撑选品的精准性。

| 事项 | 决定 |
|---|---|
| 现有流程 | **冻结**，不再扩展。旧 pilot 已无使用价值；ECS 上的旧服务暂时保留，由用户择时处理 |
| 平台范围 | **Amazon + eBay**（2026-10-18 应需求方要求，由“只做 eBay”扩大） |
| 业务主线 | ① 跟卖选品：观察同质化店铺的新品和销量，结合开学、节假日等节点发掘线索，再对比供应商价格核算成本；② 品牌选品（品类洞察）：本期一起做 |
| 数据层 | **本期重点**。接入 eBay 官方接口、DataForSEO、Jungle Scout、Helium 10、卖家精灵，并扩展 Keepa、Amazon SP-API 等更多数据源；数据层按“可插拔数据源”设计（第 3 节） |
| 框架 | 方案 A：用 `../saas-template` 的 `create-project --target selfhost` 在**本仓库 main 分支**上生成新项目 |
| 部署 | A2：全部服务运行在新加坡 ECS。Docker Compose 部署由 saas-template 提供，**不在本方案范围内** |
| 模板模块 | 保留 auth、admin、db、jobs、ai、storage、ui、shared、config；billing 与 credits 保持开启但**不接任何支付渠道**（AI 额度依赖套餐，见 14.1）；关闭营销页、博客、i18n、waitlist、newsletter、public-api |
| 账号与审批 | 团队共用一个账号；平台不做分工、指派和审批，也不记录“谁做的”。UI 稿中的**评审中心去掉**，改为工作台的“待决定”队列 |
| AI 数据分析助手 | **后置**，本期不做。AI 只用于商品簇归并、差评痛点归纳、推荐理由和差异化建议 |
| UI 实现 | 不引入 antd；用模板的 Tailwind + shadcn（`packages/ui`），把设计稿的配色、字体、圆角、阴影映射为主题变量；图表用 ECharts |
| 类目与物流 | 不锁定类目；选品方向、物流方案（eBay 直发 / 海外仓，Amazon FBA / FBM）都是可增删改的配置 |
| 额度 | eBay Browse 每天硬上限 5000，安全线 4500，绝不超额；其他数据源各自设置额度或费用上限（3.5） |
| 账号 | eBay、Amazon 卖家账号、各付费工具按“会有账号”设计；每个数据源接入的第一步是用真实凭据核验字段 |
| 季节数据 | DataForSEO（Google Trends + 关键词月搜索量历史），Amazon 站内搜索量由卖家精灵 / Jungle Scout / Helium 10 补充 |
| 风险提示 | 同款同货源和同款微改良都提示；本地品牌库 + VeRO 名单 + 检索链接，不接付费商标/专利接口 |
| 算法 | 选品算法 + 回测 + 置信度 + 算法准备度；权重等权起步，团队可调 |
| 命中标准 | 默认推荐后 30 天内商品簇销量增量 ≥ 30 件，且竞品中位价跌幅 ≤ 15%；可配置 |
| Terapeak 导入 | 模板 A 和 B 都要做，但 **hold**，等与合作方沟通 |

## 1. 设计原则

1. **系统先给线索，人只做判断。** 数据每天自动采集；人每天只花 15–30 分钟看线索、做决定。
2. **一条线索只有一个状态。** 不设标准版本、评估快照、多级审批。
3. **钱算清楚再动手。** 判断跟不跟卖的唯一硬门槛是利润。
4. **从节点倒推时间。** 根据节点日期倒算最晚决定日，提醒在窗口内做决定。
5. **证据不足要如实显示。** 缺失不补零；冷启动期不假装有可信推荐。
6. **每个数都能追溯。** 任何数值都带来源、获取时间、获取方式（官方 / 第三方估算 / 推算 / 手工导入）；多个来源不一致时并列展示，不悄悄取一个。

## 2. 总体流程

```
[0 配置]  选品方向（平台/站点/类目/关键词/店铺池）· 物流方案 · 成本参数 · 节点日历 · 品牌库
   ▼
[1 数据]  数据中心：多数据源按额度自动同步 + 无接口时文件导入 → 统一数据模型（带来源）
   ▼
[2 算法]  信号计算 → 硬门槛 → 综合评分 → 置信度
   ├────────────────────────────┐
   ▼                            ▼
[3a 跟卖选品]  候选列表          [3b 品牌选品]  品类洞察（搜索趋势、新品、差评痛点、竞品矩阵）
   ▼  关注 / 忽略 / 稍后          ▼  生成品类报告，可从中挑出商品转为线索（多为微改良）
[4 核算]  供应商 × 物流方案 × 跟卖方式，并排对比利润
   ▼
[5 决定]  工作台“待决定”队列：跟卖 / 放弃（选原因）→ 进入选品档案库
   ▼
[6 验证]  影子推荐自动打标签 + 实际跟卖回看 → 回测 → 校准算法和置信度
          └──────────────── 反馈回 [2] ────────────────┘
```

线索状态：

```
新线索 → 关注 → 核算中 → 待决定 → 跟卖 → 已上架 → 已回看
   ├──→ 稍后（到期回到新线索）          └──→ 放弃（选原因）
   └──→ 忽略（选原因）
```

- 核算完成（至少一个组合算出利润）即进入“待决定”；超过最晚决定日仍未决定的，在队列中标红。
- 所有推荐不论人有没有处理，都自动进入影子回测。

### 3.3 架构

```
                         ┌──────────── 数据中心（页面）────────────┐
                         │ 数据源状态 · 同步记录 · 数据预览 · 导入 · 数据质量 │
                         └──────────────────────────────────────────┘
调度（每日 02:00 SGT 起）        文件导入（CSV / Excel）
        │                              │
        ▼                              ▼
  同步任务（按数据源分队列，     导入映射（列名识别 + 手动对应）
  队列级并发与速率限制）                │
        │  ① 事务内预扣额度             │
        ▼                              │
  连接器 Connector ─② 原始响应→ 对象存储（保留 90 天，可回放）
        │  ③ 归一化（纯函数，用存档夹具测试）
        ▼                              ▼
  统一数据模型：商品 / 卖家 / 关键词 / 评论 / 费用 + 观测值（带来源、时间、方式）
        │
        ▼
  数据质量检查（缺失、突变、来源间差异） → 信号与算法
```

**连接器契约**（`packages/datasources`）：

```ts
interface SourceConnector {
  id: SourceId                       // 'ebay-browse' | 'keepa' | 'jungle-scout' | …
  marketplaces: Marketplace[]        // 'ebay-us' | 'amazon-us' | …
  capabilities: DataKind[]           // 3.2 的数据类型
  budget: BudgetSpec                 // 单位（次 / 令牌 / 美元）、周期、硬上限、安全线
  probe(ctx): Promise<ProbeReceipt>  // 凭据是否可用、关键字段是否返回
  fetch(task, ctx): Promise<FetchResult>  // 原始响应 + 归一化后的实体与观测值
}
```

要点：

- **凭据**放在部署层的受限 secret 文件（`*_FILE`），数据库只存启用状态和非敏感配置；页面只显示“已配置 / 未配置 / 校验失败”。
- **观测值**统一为长表：`实体 × 指标 × 日期 × 来源 → 数值 + 获取方式 + 原始响应引用`。同一指标多来源并存，不覆盖。
- **主值规则**：每个指标按团队配置的来源优先级取主值；同时计算来源间差异，差异大时降低置信度（第 11 节“来源一致性”）。回测积累后，可按各来源的预测准确度调整优先级。
- **幂等**：同一来源、同一实体、同一日期的观测重复写入只保留最新一次，历史版本留在原始响应里。
- **回放**：归一化逻辑修改后，可以从对象存储里的原始响应重新生成观测值，不再花额度。

### 3.4 无接口时的文件导入

Helium 10（未确认 API 前）、各工具的手动导出、供应商报价表都走统一导入：

1. 上传 CSV / Excel，选数据源和导入模板（如“Helium 10 Black Box 导出”“卖家精灵选产品导出”）；
2. 自动识别列名，识别不了的手动对应，对应关系保存为模板供下次复用；
3. 补填上下文（站点、日期、查询条件）；
4. 预览校验：缺失保持为空，不补零；单位和币种显式确认；
5. 确认导入，观测值的获取方式记为“手工导入”，附原文件引用。

### 3.5 额度与费用

| 数据源 | 预算单位 | 默认上限（可调） | 机制 |
|---|---|---|---|
| eBay Browse | 次/天 | 硬上限 5000，安全线 4500 | 事务内预扣，扣不到顺延次日；记录 eBay 返回的限额信息对账 |
| Keepa | 令牌/分钟 | 按套餐 | 队列速率限制 + 响应中的剩余令牌校准 |
| Jungle Scout / 卖家精灵 / Helium 10 | 次/月 | 按套餐或合同 | 月度预算按日均分配，允许当日结余滚动 |
| DataForSEO | 美元/月 | 待定 | 按任务单价预扣金额 |
| SP-API | 次/秒（官方限流） | 按接口 | 队列速率限制，遇 429 退避 |

eBay 每日调用估算（与上一版一致，约 1000 次/天，远低于安全线）：

| 任务 | 方式 | 估算每日调用 |
|---|---|---|
| 店铺新品 | `search` + `filter=sellers:{…}` + `sort=newlyListed`，每店 1–2 页 | 30 × 2 = 60 |
| 热点 listing 快照 | `getItems` 每次 20 个 | 2000 ÷ 20 = 100 |
| 普通 listing 快照 | 每 3–7 天轮询 | ~100 |
| 方向扩展 | 类目 + 关键词搜索 | ~200 |
| 新 listing 详情补全 | `getItem` | ~500 |

- **待实测：** `getItem` / `getItems` 是否返回 `estimatedAvailabilities[].estimatedSoldQuantity`。若只有 `getItem` 返回，热点快照改为逐个查询（约 2500 次/天，仍在额度内）；若都拿不到，用可售量减少近似销量，并下调“数据覆盖”置信度。
- eBay Marketplace Insights 不对新用户开放，eBay 销量只能靠快照差分。

### 3.6 数据质量

每次同步后自动检查并在数据中心列出：

- 缺失：关键字段为空的比例（例如 Amazon 商品缺销量估算）；
- 突变：价格、销量、BSR 相对前一日的异常跳变；
- 来源差异：同一商品不同来源的销量估算相差超过阈值（默认 50%）；
- 新鲜度：每个方向最近一次成功同步距今的时长；
- 同步失败：进入死信的任务及原因（不含凭据）。

## 5. 跟卖选品算法

### 5.1 维度（每个商品簇一组分数，0–100）

设计稿的 6 个维度和原方案的 7 个信号合并为以下 7 个维度，界面沿用设计稿的“评分维度管理”形式：

| 维度 | 设计稿对应 | 计算 | eBay 输入 | Amazon 输入 |
|---|---|---|---|---|
| 市场需求 | 市场容量 | 簇 7 天销量增量及相对 30 天均值的加速度 | 快照差分 | 多来源销量估算（主值）、BSR |
| 增长与季节 | 增长趋势 | 目标销售窗口内的季节指数 × 历年规律稳定性，叠加近 90 天增长 | DataForSEO | DataForSEO + 站内关键词搜索量 |
| 同行扩散 | （新增） | 14 天内上架同簇商品的对标店铺数，以及上新的时间集中度 | Browse 店铺新品 | Keepa / 卖家精灵的卖家新品 |
| 利润空间 | 利润空间 | 竞品中位价下、各物流方案中最优的估算毛利率 | 成本参数 | SP-API 费用预估 + 成本参数 |
| 竞争强度（反向） | 竞争强度 + 品牌壁垒 | 卖家数增长、最低价下滑、头部卖家/品牌份额、评论数门槛 | 快照 | 卖家数历史、评论数、头部份额 |
| 供应与时效（反向） | 供应链难度 | 最晚决定日余量、货源数量与报价可信度、MOQ | 核算 | 核算（含 FBA 入库时长） |
| 合规与侵权（一票否决） | 合规风险 | 见第 7 节 | 规则 | 规则 |

最晚决定日：

```
最晚决定日 = 节点销售开始日 − 物流时长（Amazon 再加 FBA 入库上架时长）− 采购时长（微改良再加打样天数）− 上架准备
例：返校季 7/15 起卖，海运 35 天 + FBA 入库 10 天，采购 10 天，上架 3 天 → 5/18 前必须决定
```

### 5.2 打分流程

1. **硬门槛**（不通过就不推荐，但列表中可查看原因）：合规与侵权低于一票否决阈值（默认 30）；所有物流方案都来不及；所有物流方案的毛利率都低于底线（默认 15%）。
2. **综合分** = 各维度加权和（反向维度取 100 − 分数）。等权起步，团队可调；回测样本足够后用逻辑回归等可解释模型拟合权重，团队确认后启用。权重修改只影响之后的评估，已冻结的影子推荐保留当时的权重版本。
3. **等级**：推荐 ≥ 75、谨慎 50–74、不推荐 < 50（设计稿规则）；准备度为“冷启动”时不显示等级，只显示“未验证”。
4. **置信度**与综合分分开显示；列表按“综合分 × 置信度”排序，高分低置信标为“值得关注但证据不足”。

### 5.3 商品簇归并

依次使用：GTIN/UPC/ePID/ASIN 关联 → 标题向量相似 → 图片相似。跨平台归并（同一商品在 Amazon 和 eBay）作为簇的属性展示，信号仍按平台分别计算。每个成员记录归并置信度；人可以手动拆分或合并，修正记录作为训练样本。AI 用量走 `packages/ai` 的预算。

## 8. 核算

- 每个商品可挂多家供应商：链接 + 手填报价（单价、数量阶梯、MOQ、重量和尺寸）。报价可信度分两档：公开价、已确认报价。
- 对比矩阵：供应商 × 物流方案 × 跟卖方式，每格显示落地成本、保本价、竞品中位价下的毛利率、最晚决定日。系统高亮最优组合，人选一个组合做决定。
- 设计稿的“成本瀑布图”用于展示所选组合：采购 → 头程 → 平台费用 → 配送/尾程 → 广告 → 退货预留 → 净利润。

| 成本项 | eBay | Amazon |
|---|---|---|
| 采购价 | 报价（计划数量对应阶梯） | 同左 |
| 头程 | 物流方案 × 重量体积 | 物流方案（到 FBA 仓） |
| 平台费用 | 成交费率 + 单笔固定费 | 佣金费率 |
| 配送/尾程 | 直发运费或海外仓尾程 | FBA 配送费（SP-API 预估优先，失败时用费率表） |
| 仓储 | 海外仓仓租 | FBA 月仓储费、入库配置费 |
| 广告、退货预留、改款费分摊 | 成本参数 / 跟卖方式 | 同左 |
| 竞品价格分布 | 采集数据 | 采集数据 |

## 9. 决定、待决定队列与选品档案库

- **待决定队列**（工作台首页）：核算完成的线索按最晚决定日排序；临近（默认 7 天内）标橙，已过标红。
- **跟卖**：填首批数量、目标售价、计划上架日。**放弃**：选原因（利润不够 / 竞争太多 / 时间来不及 / 货源不行 / 侵权风险 / 其他）。
- 决定后进入**选品档案库**，保存决定当时的分数、核算组合和数据快照引用；品类研究报告也归档在这里。
- 跟卖后 30 天提醒回看：录入实际销量和售价，与当初判断对比。

## 10. 回测与验证

| 数据 | 能否回测 | 方式 |
|---|---|---|
| 季节曲线 | 从第一天就能 | 5 年 Trends 滚动验证：用前 N 年预测下一年的高峰时间和幅度 |

| Terapeak 导入 | hold | 第 15 节 |

## 11. 置信度与算法准备度

### 11.1 单条线索的置信度

| 维度 | 衡量什么 | 示例指标 |
|---|---|---|
| ① 数据覆盖 | 证据量够不够 | 快照天数、同簇商品数、覆盖店铺数、销量字段是否可得 |
| ② 数据新鲜度 | 是不是最新的 | 最近一次成功同步距今小时数 |
| ③ 信号一致性 | 独立信号是否互相印证 | 需求、季节、扩散中同时为正的个数 |
| ④ 来源一致性（新增） | 多个数据源是否说法一致 | 销量估算的来源间离散度；只有单一来源时为“未交叉验证” |
| ⑤ 归并可信度 | 是不是真的同款 | 簇内标题、图片、属性相似度 |
| ⑥ 季节规律稳定性 | 往年规律靠不靠谱 | 历年曲线相关系数、高峰周年际波动 |
| ⑦ 成本确定性 | 账算得准不准 | 报价类型、物流模板完整度、费用是否来自官方预估 |
| ⑧ 时间余量 | 来不来得及 | 剩余天数 ÷ 所需提前期 |
| ⑨ 竞争稳定性 | 价格和卖家数是否剧烈变动 | 价格波动率、卖家数增速 |
| ⑩ 历史命中率 | 同类推荐过去准不准 | 同平台、同信号类型、同方向的回测命中率，Wilson 置信下界 |

### 11.2 算法准备度（按平台 × 方向 × 信号类型分别计算）

| 等级 | 条件（初始值，可调） | 界面表现 |
|---|---|---|
| 冷启动 | 样本 < 20 | 只展示信号，不给等级，标注“未验证” |
| 观察期 | 样本 20–50 | 展示推荐，置信度上限为“中” |
| 可用 | 样本 ≥ 50，命中率下界 ≥ 基线 | 正常推荐 |
| 可信 | 样本 ≥ 100，权重已校准，最近 3 个月命中率稳定 | 可作为优先级依据 |

基线是同方向随机抽取新品的命中率。准备度界面分别显示“影子推荐样本”“历史回放样本”（Amazon / Keepa）和“导入样本”（Terapeak，hold），历史回放样本权重低于影子推荐。

### 14.1 项目生成

saas-template 的自托管目标已完成（DBOS 队列、定时任务、多步任务，新加坡 ECS 实测）。生成参数：

```
pnpm create-project --name product-res --domain <待定> --target selfhost \
  --output <临时目录> --image-namespace ghcr.io/ustclhx/product-res \
  --ai text --billing '' --billing-enabled true --credits-enabled true \
  --marketing false --i18n false --locale zh --features '' --oauth ''
```

## 18. 风险

| 风险 | 应对 |
|---|---|
| eBay Production 账号、SP-API 开发者注册的审批门槛 | 与 M0 并行，尽早申请 |
| 第三方工具的 API 权限、价格或条款与预期不同（尤其 Helium 10） | 每个数据源先核验；没有 API 的走文件导入；数据层与具体工具解耦 |
| 多个来源的 Amazon 销量估算差异大 | 并列展示，计算来源一致性，回测后按准确度调整优先级 |
| `estimatedSoldQuantity` 拿不到或覆盖不全 | 用可售量减少近似，下调数据覆盖置信度 |
| 付费数据源费用失控 | 每个来源设硬上限，事务内预扣，超限即停 |
| 商品簇归并不准导致信号失真 | 显示归并置信度；支持手动拆分/合并 |
| 冷启动期没有可信推荐 | 界面如实显示“冷启动”；Amazon 用 Keepa 历史回放缩短冷启动 |
| 评论数据来源不确定，差评痛点可能做不出 | M1b 核验评论来源；拿不到时品类洞察隐藏该模块并说明原因 |
| 季节曲线是搜索热度，不等于成交 | 只作为“增长与季节”的输入，与站内数据交叉验证 |
